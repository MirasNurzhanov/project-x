# C1 — Credentialed CORS on all URLs + wildcard CSRF trusted origins can expose Django admin

## Status
FIXED

The code fix is verified by tests against both the new and the unmodified code. The **live Railway
deployment is not verified** and needs environment variables set **before** this change is pushed
to `main` (see *Compatibility / deployment notes*). That part is NEEDS EXTERNAL ACTION.

## Severity
Critical

## Original problem
Review, pages 4–5: four settings combined so that any website could make credentialed
cross-origin requests to any path and read the response. The API uses bearer tokens, but `/admin/`
authenticates with a session cookie. A page on a free `*.vercel.app` or `*.railway.app` subdomain,
opened by a staff member with a live admin session, could read admin HTML (including the CSRF
token) and then POST admin actions. Those POSTs passed Django's origin check because both
wildcards were trusted CSRF origins. The result is full admin compromise: bans, moderation
actions, and every user row, including stored precise coordinates.

## Root cause
At `HEAD` (`5eaf830`), `core/settings.py`:

| Line | Setting | Effect |
|---|---|---|
| 341 | `CORS_ALLOW_ALL_ORIGINS = not DEBUG` | Inverted: allow-all exactly when `DEBUG` is off, i.e. production |
| 348 | `CORS_ALLOW_CREDENTIALS = True` | corsheaders 4.9.0 (`middleware.py:112-118`) then echoes the request `Origin` and adds `Access-Control-Allow-Credentials: true` instead of `*` |
| 339 | `CORS_URLS_REGEX = r'^.*$'` | Every path is a CORS surface, including `/admin/`, `/legal/` and `/api/internal/` |
| 334-337 | `CSRF_TRUSTED_ORIGINS` default `https://*.railway.app,https://*.vercel.app,…` | Django `csrf.py` `allowed_origin_subdomains` trusts every subdomain of both shared hosts |

## Investigation
- `core/settings.py` (lines above), `core/urls.py:31` (`path("admin/", admin.site.urls)`).
- `corsheaders/middleware.py` 4.9.0: `is_enabled` matches `CORS_URLS_REGEX` against
  `request.path_info`; `add_response_headers` lines 105–118 echo the origin when allow-all and
  credentials are both on. `corsheaders/conf.py` reads settings on each access, so
  `override_settings` is effective in tests.
- `django/middleware/csrf.py` 5.2.14: `_origin_verified` (271–296) accepts
  `scheme://get_host()` as same-origin before consulting `CSRF_TRUSTED_ORIGINS`. The admin
  therefore needs no trusted origins at all.
- Who needs cross-origin browser access and credentials:
  - `REST_FRAMEWORK` authenticates only with `users.authentication.SuspensionAwareJWTAuthentication`.
  - Grep across `backend/project-x`, `aura-mobile` and `websitefront` for `SessionAuthentication`,
    `login_required`, `staff_member_required`, `csrf_exempt`, `withCredentials` and
    `credentials: 'include'` found no matches.
  - `websitefront/project-x-frontend/src/services/api.js` uses axios with a bearer header, sends
    the refresh token in the request body, and sets no `withCredentials`.
  - `aura-mobile/services/api.ts` is native HTTP, so CORS does not apply.
  - The only cookie-authenticated surface is `/admin/`.
- `/api/internal/` (`swifts/worker_urls.py`) is machine-to-machine, token-gated, and needs no CORS.
- **Reproduced against unmodified code** (see Verification):
  - With a staff session, `GET /admin/users/user/` from `Origin: https://attacker.vercel.app`
    returned `access-control-allow-origin: https://attacker.vercel.app` and
    `access-control-allow-credentials: true`.
  - A CSRF-token-bearing admin POST from that origin returned `200` instead of `403`.

## Changes made
`core/settings.py`:
- `CORS_URLS_REGEX = r'^/api/(?!internal/)'`. `/admin/`, `/legal/`, `/static/` and
  `/api/internal/` get no CORS headers.
- `CORS_ALLOW_ALL_ORIGINS = False` in every environment.
- `CORS_ALLOW_CREDENTIALS = False`. No client uses cookies cross-origin (see Investigation).
- `CORS_ALLOWED_ORIGINS` comes from the environment only.
  - Production default is empty.
  - Development (`DEBUG=True`) default is `http://localhost:3000`, `http://localhost:5173`,
    `http://127.0.0.1:3000` and `http://127.0.0.1:5173`.
  - The hardcoded `192.168.68.113` LAN origins and the Vercel origin were removed from defaults.
- `CSRF_TRUSTED_ORIGINS` comes from the environment only, defaulting to empty. Any entry
  containing `*` raises `ImproperlyConfigured` at startup, in every environment.
- `ALLOWED_HOSTS` comes from the environment and is required in production. This is shared with
  M11; see [M11.md](M11.md).
- The existing `_csv_setting` helper moved to the top of the module and gained a `default`
  parameter, so these settings reuse it. The Google/Apple client-id settings still call it, with
  unchanged behaviour.

`core/test_security.py` is new (see Tests). `.env.example` documents the variables.

**Deviation from the review's suggested fix:** the review proposed `CORS_ALLOW_ALL_ORIGINS = DEBUG`
and a hardcoded production CSRF origin. The batch requirements say production must never allow all
origins and that exact origins must come from deployment configuration. So allow-all is off
everywhere, no production origin is hardcoded, and credentials are also disabled as an extra layer.

## Why this fixes it
The exploit chain is now broken at four independent points. Any one of them alone stops the
cross-origin admin read:
1. `/admin/` does not match the CORS regex, so no `Access-Control-Allow-*` header is ever sent for
   it. The browser refuses to expose the response to the attacking page.
2. Even on `/api/`, `Access-Control-Allow-Credentials` is never sent, so a browser will not expose a
   response to a request made with ambient cookies.
3. Allow-all is gone, so only exact, configured origins receive `Access-Control-Allow-Origin`.
4. No trusted CSRF origin can contain a wildcard, so a POST carrying `Origin:
   https://<anything>.vercel.app` fails Django's origin check with `403`. Same-origin admin use
   still passes, because Django accepts `Origin == scheme://host`.

environment. `.env` is ignored, so the real module wiring is what gets tested.

## Compatibility / deployment notes
**Do these on Railway before pushing to `main`, which auto-deploys.** Settings are imported by the
`release`, `web` and `worker` Procfile processes. Any Railway service running them with
`DEBUG=False` and no `ALLOWED_HOSTS` exits at startup with `ImproperlyConfigured`. The repo does
not show whether Railway keeps the previous deployment serving in that case, so treat it as a
possible outage.

1. **Set `ALLOWED_HOSTS`** on every service that runs this code. Include:
   - `project-x-production-3261.up.railway.app`, and any custom domain;
   - the private hostname the Go moderation worker uses in `DJANGO_BASE_URL`, if it calls Django
     over Railway's private network (`services/go-moderation/main.go:47-50` says it does on
     Railway);
   - `healthcheck.railway.app`, if a Railway healthcheck path is configured. Railway documents this
     as the healthcheck `Host`; confirm against current Railway documentation.
2. **Inspect existing `CSRF_TRUSTED_ORIGINS` and `CORS_ALLOWED_ORIGINS` variables.** A wildcard in
   `CSRF_TRUSTED_ORIGINS` now blocks startup. The admin needs no trusted origins, so the variable
   can be deleted or left empty.
3. **If the web frontend (`project-x-frontend-alpha.vercel.app`) is still in use**, set
   `CORS_ALLOWED_ORIGINS=https://project-x-frontend-alpha.vercel.app`. Until then, browsers block
   its API calls; it previously worked only through allow-all. The mobile app is unaffected: it
   uses native HTTP and no cookies.
4. **Post-deploy spot check**, runnable by anyone:
   - `curl -sI -H 'Origin: https://attacker.vercel.app' https://<host>/admin/login/` must show no
     `access-control-allow-origin`.
   - The same request against `/api/users/terms/` must show no `access-control-allow-credentials`.

**Local development:** `DEBUG=True` needs no new variables. `docker-compose.yml` now sets
`ALLOWED_HOSTS=localhost,127.0.0.1,django`, because the Go services call `http://django:8000`.
Testing runserver from another LAN device needs `ALLOWED_HOSTS` and, for browser clients,
`CORS_ALLOWED_ORIGINS`.

## Remaining risk
- **Production values are unverified.** Nothing in the repo shows the live `DEBUG`, `ALLOWED_HOSTS`,
  `CORS_ALLOWED_ORIGINS` or `CSRF_TRUSTED_ORIGINS` values, or that the steps above were done.
- The admin is still at the guessable `/admin/`, with no IP allow-list, SSO or 2FA. The review
  suggests this as further hardening; it is outside this finding.
- Channels WebSocket routes (`core/asgi.py`) have no `AllowedHostsOriginValidator`. They
  authenticate by JWT, not cookie, so they are not part of this chain. Noted only.
- An allowed origin that is itself compromised can still read `/api/` responses. It can only do so
  with tokens it already holds, since credentials are off.
