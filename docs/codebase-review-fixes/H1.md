## Severity and original problem
HIGH. Approx-Codebase-Review.pdf, page 6: socket authentication loaded a user directly from an access token without the REST suspension check. Connected clients retained a stale user object and could continue messaging after suspension.

## Root cause and changes
- `core/middleware.py` now uses `SuspensionAwareJWTAuthentication` for token validation and user authentication, reusing the canonical `User.suspension_detail()` policy. Invalid tokens, inactive/deleted accounts, bans and current suspensions are refused with the existing socket close code 4001.
- New `core/websockets.py` provides a shared `SuspensionAwareConsumer`. It reads current account standing before connection, each inbound message and outgoing channel event. Disconnect cleanup is preserved.
- `friends/consumers.py` and `clubs/consumers.py` use that base for direct chat, club chat and user notifications. Their relationship/membership checks remain intact.
- Both message persistence paths recheck standing after asynchronous moderation, preventing a suspension during screening from creating a message or push notification.
- Expired temporary suspensions remain allowed according to the canonical policy. No separate suspension flag or expiry calculation was introduced.

## Operational boundary
Idle sockets close on their next inbound message or outgoing channel event; no timer or admin broadcast is required for enforcement. A message that completed before suspension is not retroactively deleted. The checks add database reads on socket activity. Physical deployment, multi-worker behavior and live network sockets were not exercised.
