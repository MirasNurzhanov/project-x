# H2 — Club "invite" force-joins users without consent and ignores blocks

## Status
FIXED

An owner's invite now creates a pending `ClubInvitation`. Membership exists only after the invitee
accepts. Blocked, missing, self, inactive and privately listed accounts all get one identical 404.
Backend and mobile tests pass, and the new tests fail against the old code. No deployment was
performed.

Two caveats:
- The mobile screens were not exercised on a device or simulator.
- Invitees on older app builds cannot accept until they update (see *Compatibility*).

## Severity
High

## Original problem
Review, page 7: `ClubInviteView.post` did not invite anyone; it added them:
```python
target = get_object_or_404(User, pk=user_id)
member = ClubMember.objects.create(user=target, club=club)
notify_club_invite(club, request.user, target)
```
There was no consent, no block check in either direction, no privacy check and no rate limit. A
forced member could read the club's whole history and appear in its roster. A blocked harasser
could put their target back in a shared room and push a notification to them.
`get_object_or_404(User, …)` also distinguished existing from non-existent user ids.

## Root cause
The endpoint wrote `ClubMember` directly (`clubs/views.py:314-334` at the start of this batch). The
project already modelled consent for social actions with `HiRequest` and `FriendRequest`
(pending → accepted/declined, answered by the receiver), and resolved targets through
`users.visibility.visible_users` / `not_found()`. The club invite used neither.
`notify_club_invite` announced a completed membership ("added you to …").

## Investigation
- **`clubs/views.py`:**
  - `ClubInviteView` was owner-only, not location-gated, and created the membership directly.
  - `ClubJoinView` requires `visibility.can_see`.
  - `_accessible_club_or_none`: membership outranks location (`clubs/visibility.py` docstring).
- **`clubs/models.py`:** `ClubMember` has `unique_together (user, club)`. No invitation model
  existed; the latest migration was `0014_alter_clubmessage_moderation`.
- **`users/visibility.py`:**
  - `visible_users()` drops both directions of a block and self.
  - `relationship()` and `is_approved_viewer()` identify friends and connections.
  - `not_found()` is the canonical 404.
- **`users/views.py` `UserSearchView`:** the mobile invite modal finds people through
  `visible_users(me, discoverable_by='username')`, which honours the username-search opt-out.
- **Existing request pattern:** `friends/views.py` `SendHiView` / `AcceptHiView` / `DeclineHiView`
  (M19): `get_or_create` on a unique pair, `transaction.on_commit` push for new rows only, retained
  decline, and conditional pending-state updates.
- **Notifications:**
  - `notifications/utils.py` `notify_club_invite` wrote a `club_invite` activity row and pushed
    `type: 'club'`.
  - `notifications/badges.py` counts pending Hi and friend requests plus unread activity.
  - `notifications/test_push_targets.py` pinned the old "added" alert.
- **Mobile:**
  - `services/clubs.ts` `invite` → `POST /api/clubs/<id>/invite/<user_id>/`.
  - `app/clubs/[id].tsx` `useClubInvite` treated success as "added" and refetched the roster.
  - `services/alerts.ts` loads Hi and friend requests as accept/decline `AlertRequest` rows.
  - `components/alerts/AlertRow.tsx` renders them.
  - `services/notificationRouting.ts` already routes push `type: 'request'` to the alerts feed.
- **Existing tests:** no club test exercised `/invite/`. Only
  `notifications/test_push_targets.py::test_an_invitation_tells_the_person_who_was_added` covered
  the notification.

## Changes made

### Backend
- **`clubs/models.py`: new `ClubInvitation`**, shaped like `HiRequest`:
  - `club`, `sender` (nullable, `SET_NULL`), `receiver`, `status`
    (`pending` / `accepted` / `declined`), `created_at`, `responded_at`;
  - `UniqueConstraint(club, receiver)` named `club_invitation_one_per_receiver`.
- **`clubs/models.py`: `ClubInvitationQuerySet.pending_for(user)`** is the single definition of an
  answerable invitation: pending, club active, receiver not already a member, and no block in
  either direction between receiver and sender (`EXISTS` subqueries).
- **`clubs/migrations/0015_clubinvitation.py`:** a single additive `CreateModel` with the
  constraint. No data migration.
- **`clubs/views.py` `ClubInviteView`**, same URL:
  - Owner-only, as before (403 for others).
  - The target is resolved by `_invitable_user`: `visible_users(owner)` (blocks both ways, self),
    `is_active=True`, and either `discoverable_by_username` or an approved relationship
    (friend or connection). Anything else, including bad ids, gets `user_visibility.not_found()`.
  - Existing members get a 400 `User is already a member.`
  - `get_or_create` runs inside `transaction.atomic()`:
    - a new invitation returns 201 and schedules the push with `transaction.on_commit`;
    - a repeat returns 200 with the same row and no push;
    - a declined invitation stays declined, 200 with no push;
    - an accepted invitation whose receiver has since left is reopened as pending with a new push
      (201), so coming back needs a fresh acceptance.
  - Rate limited with the existing `social_request` scope, shared with Hi and friend requests.
- **New endpoints in `clubs/urls.py`**, routed before `<int:pk>/`:
  - `GET /api/clubs/invitations/`: the requester's `pending_for` invitations, newest first.
  - `POST /api/clubs/invitations/<pk>/accept/`: a conditional update pending → accepted scoped by
    `pending_for`, then `ClubMember.get_or_create`, inside one transaction. Returns 201 with the
    membership; not answerable → canonical 404.
  - `POST /api/clubs/invitations/<pk>/decline/`: a conditional update pending → declined. Returns
    204; not answerable → 404.
- **`clubs/serializers.py` `ClubInvitationSerializer`:** `id`, `club {id, name}`, `sender`,
  `receiver`, `status`, `created_at`, `responded_at`.
- **`notifications/utils.py` `notify_club_invite(invitation)`:** push only, like a Hi.
  - Title `👥 Club invitation`, text `@owner invited you to join <club>`.
  - `data={'type': 'request', 'club_id', 'club_name'}`, category `social`.
  - It no longer writes a `club_invite` activity row, which would list the same invitation twice.
- **`notifications/badges.py`:** the alerts badge adds `ClubInvitation.objects.pending_for(user)`,
  in the same single query.

### Mobile (`aura-mobile`)
- **`services/alerts.ts`:**
  - `AlertRequest.kind` gains `'club'`, with an optional `club {id, name}`.
  - `loadAlerts()` also fetches `/api/clubs/invitations/`.
  - `requestActionUrl()` maps `club` to `/api/clubs/invitations/<id>/<action>/`.
- **`components/alerts/AlertRow.tsx`:** the request row reads "Invited you to join <club>" and
  reuses the existing Accept/Decline buttons.
- **`app/clubs/[id].tsx`:** the invite modal marks invited people "Invited" (disabled) instead of
  refreshing the roster, since nobody has joined yet. A 404 shows "This person can’t be invited."
- **Push routing:** unchanged; `type: 'request'` already opens alerts.

## Why this fixes it
- **Consent.** No code path creates a `ClubMember` from an owner's action any more. The only new
  membership path is the invitee's own `accept`, which requires a pending invitation answerable by
  that exact user.
- **Blocks.**
  - A block in either direction hides the target at invite time.
  - A block created after the invite removes it from the list, the badge, accept and decline,
    because all of them read `pending_for`.
- **Enumeration.** Missing, blocked, self, inactive and privately listed accounts all return the
  same `{'detail': 'Not found.'}` 404, the project's canonical `not_found()`. Visible accounts
  still get ordinary responses, the same boundary M19 draws for Hi requests.
- **Harassment and flooding.**
  - One row per person per club.
  - Repeats never re-notify.
  - A decline cannot be reset by the owner.
  - Invites share the per-user `social_request` budget (30/hour by default).

## Compatibility / deployment notes
- **Migration.** `0015_clubinvitation` is additive and applied by the `release` step's `migrate`.
- **API.**
  - The invite URL is unchanged, but the success body is now an invitation (`status`, `club`,
    `sender`, `receiver`) instead of a membership.
  - New endpoints: `GET /api/clubs/invitations/` and `POST /api/clubs/invitations/<id>/accept|decline/`.
- **Older app builds.**
  - An owner's invite still succeeds, but the old app thinks the person was added (it refetches a
    roster that does not include them).
  - An invitee on an old build receives the push but has no list entry to accept, because old
    builds do not load `/api/clubs/invitations/`. They must update to accept; they can still join
    from discovery if the club is in their area.
  - Ship the mobile change with, or soon after, the backend deploy.
- **Existing memberships.** Memberships created by the old force-join are left untouched: consent
  cannot be reconstructed after the fact. Old `club_invite` activity rows ("added you to …") stay
  in history.
- **Location.** An invitee can see the invited club's name even when outside its area. That is
  deliberate: the owner vouched for them, and on acceptance membership outranks location, as
  before.

## Remaining risk
- **Mobile UI not run** on a device or simulator.
- **Old app builds** cannot accept invitations (see above).
- **Concurrency not run on PostgreSQL.** Concurrent duplicate invites rely on
  `get_or_create` + `UniqueConstraint`, the same mechanism M19 verified on PostgreSQL for
  `HiRequest`. That run did not cover `ClubInvitation`. Concurrent accepts are guarded by the
  conditional update, and membership creation is idempotent.
- **Existing force-joined memberships** from before this fix remain.
- **Owner-only enumeration.** Only club owners can invite. An owner can still tell a visible,
  searchable user id from an invisible one, the same boundary accepted for Hi requests (M19).
- **Admin.** `ClubInvitation` is not registered in the Django admin.
