## Severity and original problem
HIGH. Approx-Codebase-Review.pdf, page 8: authentication views did not declare scopes, so the configured DRF `ScopedRateThrottle` did not apply to them.

## Root cause and changes
`users/views.py` now assigns scopes to password login, registration, refresh and social login. All use the existing global `ScopedRateThrottle`, cache and DRF 429/Retry-After response behavior. No custom counter or competing throttle implementation was added.

`core/settings.py` and `.env.example` expose these defaults:

| Scope | Environment variable | Default |
| --- | --- | --- |
| login | THROTTLE_LOGIN | 10/min |
| register | THROTTLE_REGISTER | 10/hour |
| refresh | THROTTLE_REFRESH | 120/hour |
| social_login | THROTTLE_SOCIAL_LOGIN | 30/min |

These are per-IP budgets with separate scopes. Registration and social login explicitly run without bearer authentication, matching the credential-establishing nature of these endpoints and preventing an Authorization header from switching their budget to a user key. Existing provider signature verification, account resolution, terms, suspension gates and response payloads are preserved.

DRF `NUM_PROXIES=0` makes throttling use `REMOTE_ADDR`, which the existing trusted-proxy uvicorn configuration resolves. A caller cannot reset a budget by rotating a raw X-Forwarded-For header. Correct deployment proxy configuration remains necessary.

## Password-login enumeration review
The installed Django ModelBackend and SimpleJWT serializer already return the same 401 payload for unknown accounts and wrong passwords. Django also performs a dummy password hash for unknown users. That behavior was retained and explicitly tested. Terms and suspension details remain behind successful password verification. Registration uniqueness validation and provider-specific error contracts were not redesigned.

## Operational boundary
Production should use the existing shared Redis cache. DRF's built-in cache throttles are approximate under concurrent bursts and do not replace perimeter abuse controls. Distributed/IP-rotation attack resistance and production Redis were not load-tested. Defaults are configurable without source changes; shared-NAT traffic may warrant tuning.
