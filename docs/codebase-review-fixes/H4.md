# H4 — Idempotent Swift publishing

Status: fixed in the backend and mobile client. No deployment performed.

## Cause and implementation

The composer passed a draft to `publishSwift`, which rebuilt a multipart POST on each XHR retry. `SwiftCreateSerializer` and `SwiftListCreateView` treated every attempt as a new `SwiftVideo`, including storing media and enqueueing moderation.

The composer now assigns an opaque UUID once per captured/imported take. Draft edits, automatic transfer retries and manual retries retain it. A new take receives a new key, even for the same source URI. The upload service requires and submits `idempotency_key`. Keys live with the existing in-memory draft; this change does not introduce draft recovery after an app restart.

The backend validates the UUID and binds it to the authenticated author. Migration `0010_swiftvideo_idempotency_key_and_more.py` adds the nullable column and the database constraint `unique_swift_author_take`. Null preserves existing rows and older clients; all publishes from the updated composer carry a key. Apply this migration before using the new backend code.

Keyed creation holds an author row lock before looking up the key or saving media. Concurrent retries therefore cannot upload another stored file or enqueue another moderation job. First creation returns 201; a repeated key returns 200 with the existing Swift, without revalidating or applying changed draft fields. This is first-write-wins behavior. Keys are not exposed in feed/detail responses. Different authors may independently use the same key. Deleted/removed rows reserve their key and return 404 rather than resurrecting the take.

The UI acquires its submission guard synchronously, before any async work, and immediately displays upload progress. Cancellation keeps the guard until the promise settles; success keeps it until navigation. This closes the same-render double-tap window.

## Verification

`swifts.test_publish_integrity` covers repeated/key-only retries, original-payload preservation, one media save/job, distinct keys, separate authors, database uniqueness, invalid requests, legacy requests and removed/deleted takes. Its concurrent PostgreSQL test verifies one 201, one 200, one row, one file save and one enqueue.

Mobile tests exercise automatic and manual XHR retries, missing-key refusal, same-render duplicate presses, the success guard, retry after failure and a fresh key for a new composer take. The PostgreSQL/Redis CI regression selection passed all 37 tests, with no skips. Full-suite results are recorded in H10.md.

## Boundaries

Legacy requests without keys retain their previous behavior. The author lock serializes that author's keyed publishes while media is stored. Storage uploads are not transactionally rolled back if an unrelated storage/database failure occurs; this change prevents duplicate media from competing retries, not every possible orphan-file failure.

Changed: mobile `services/swiftDraft.ts`, `services/swiftUpload.ts`, `app/swifts/compose.tsx`, upload/composer tests; backend Swift model, serializer, create view, migration and publish-integrity tests.
