# H5 — Polygon containment performs expensive Python geometry on frequent map polling

## Status
FIXED

A region's rings are now indexed once per `Region` instance, and every containment probe reuses the
index.
- **How:** the index groups edges into latitude bands. A probe does arithmetic only on edges that can
  affect its answer, using the same arithmetic as before.
- **Same answers:** containment results are identical, including the boundary-inclusive rule and the
  tolerance probes.
- **Linear size:** the index stays linear in the ring's size.

On the reproducible benchmark at 1,500 vertices (OpenStreetMap's stored maximum):
- A non-friend candidate that misses the zone went from 4.75 ms to 0.18 ms on 200-candidate polls.
- A 1,000-candidate poll of such misses takes 164 ms instead of about 4.75 s.
- Every run had 0 mismatches.

Not changed:
- **No PostGIS.**
- **The candidate ceiling stays at 1000**, because lowering it would change which people the map
  shows.

Production latency has not been measured, and no deployment was performed.

## Severity
High

## Original problem
Review, page 10:
- **Cited code:**
  - `regions/geometry.py:150-180`: `ring_contains` and `point_on_ring` loop over every vertex.
  - `regions/geometry.py:254-280`: `contains_within` probes 9 points.
  - `proximity/views.py:110`: `MAX_ZONE_CANDIDATES = 1000`.
  - `proximity/views.py:540-563`: `in_zone()` runs per candidate, per poll.
- **What:** city and district zones are tested by even-odd ray casting in pure Python.
  - A non-friend goes through `contains_within`, which probes the centre plus eight compass points.
  - A point outside the polygon but inside its bounding box therefore costs nine ring walks.
  - Each walk runs `point_on_ring` (a square root per segment) and then `ring_contains`.
- **Reviewer's benchmark (worst case per candidate):**

  | Vertices | Per candidate | ×200 candidates | ×1000 candidates |
  |---|---|---|---|
  | 1,500 | 1.89 ms | 0.38 s | 1.89 s |
  | 5,000 | 5.95 ms | 1.19 s | 5.95 s |

- **Why it matters:** `GET /api/map/nearby/` is polled by every client every ten seconds. This is
  Python CPU, so the statement timeout does not help, and one process (M20) absorbs it.
- **Suggested fixes:**
  - Compute distance-to-edge once against a precomputed edge index, instead of nine walks.
  - Run `point_on_ring` only when `tolerance_m == 0`.
  - Lower `MAX_ZONE_CANDIDATES` toward `MAX_NEARBY_MATCHES = 200`.
  - Structurally, move containment to PostGIS.

## Root cause
`Region.contains` and `Region.could_contain` passed the raw ring lists to `geometry.contains` and
`geometry.contains_within`:
- Every probe walked every edge of every ring twice. The first pass was `point_on_ring`: a dot
  product, a division, and a square root for each edge whose projection lands on the segment. The
  second was `ring_contains`.
- Nothing derived from the rings was kept between probes or candidates.

A poll therefore did up to 9 probes × up to 1000 candidates × 2 passes × every edge, all against the
same region.

## Investigation
- **Call path:** `proximity/views.py` `in_zone` (lines 540-547) → `_viewer_zone_contains` (line 144)
  → `user.zone_contains` → `users/zones.py:94-96` → `Region.could_contain(float(lat), float(lon),
  tolerance_m)`, or `Region.contains` when the tolerance is 0.
- **One region object per poll:** `user.zone_region` is a foreign key, and Django caches the loaded
  object on the user instance. Every candidate in one poll is tested against the same `Region`
  object.
- **Tolerance:** `visibility.position_tolerance_for` returns 0 for a friend and
  `APPROX_GRID_M * 0.708` (about 354 m) for anyone else.
- **Candidates:**
  - Connected people come from `[:MAX_ZONE_CANDIDATES]` (line 486).
  - Strangers come from `stranger_candidates[:MAX_ZONE_CANDIDATES]` (line 559).
  - Both slices are bounding-box prefilters with no ordering, taken before the containment test.
  - Matches are then sorted by distance and capped at `MAX_NEARBY_MATCHES = 200`, with friends
    exempt (lines 568-582).
- **Other callers of the same Region methods:** `regions/resolver.py:410`, `regions/places.py:368`,
  `regions/nominatim.py:756` and `users/serializers.py:858`. They all get the index too.
- **Geometry sizes:**
  - OpenStreetMap geometry is simplified to at most `nominatim.MAX_POINTS = 1500` points before
    storage.
  - Hand-traced geometry had no limit (H6, fixed in this batch).
- **In-place mutation:** a search for `.rings.append`, `.rings.extend`, `.rings.insert` and
  `rings[n].append` or `rings[n].insert` found nothing. No code mutates a region's rings in place.
- **Caching:** a search for `cache.set`/`get_or_set` with regions found no code that caches `Region`
  instances.
- **Baseline benchmark:** new reproducible command
  `python manage.py bench_containment --settings=core.test_settings`.
  - Seeded jagged rings with deep concavities: 1,500, 5,000 and 20,000 vertices.
  - Candidates drawn inside the bounding box: 200 per simulated poll by default.
  - Best of 3 rounds, seed 20260913.
  - A fresh `Region` per simulated poll, the way the map loads one.
  - Three modes:
    - `contains`: a friend.
    - `could_contain`: a non-friend at 354 m tolerance.
    - `could_contain (misses)`: only candidates for which all nine probes fail, which is the worst
      case.
  - Every answer is also checked against the plain ring-list functions.
  - Results are under *Verification*.

### Review suggestions considered
- **Skip `point_on_ring` whenever tolerance is above 0: not adopted.** It changes answers.
  - Take a point exactly on a boundary whose eight 354 m probes all land outside, for example the
    tip of a spike or a strip narrower than the probe spacing.
  - Today that point is inside. Without the boundary pass, its answer would depend on the ray cast's
    vertex convention.
  - Instead, the boundary pass keeps its exact rule but only does arithmetic on edges whose bounding
    box is within 4×10⁻⁷° of the probe. The expensive part almost never runs.
- **Replace the nine probes with one distance-to-edge test: not adopted.** That tests a circle
  rather than a centre plus eight compass points, and gives different answers near corners.
- **Lower `MAX_ZONE_CANDIDATES` to about 200: not adopted.** The slice is taken before containment
  and before any ordering.
  - In a dense city whose bounding box holds many people outside the outline, 200 unordered rows can
    yield far fewer than 200 matches.
  - The 200 shown would then no longer be the nearest ones.
  - That is a change to what the map shows. The ceiling stays at 1000, where a full 1,000-candidate
    poll now measures 164 ms in the worst case at 1,500 vertices.
- **PostGIS: not done**, as the batch instructions require. It remains the structural fix.

## Changes made
**`regions/geometry.py`:**
- **`PreparedRing`:**
  - Builds a ring's edges once, with the same vertex pairing as `ring_contains` and
    `point_on_ring`, plus each edge's bounding box.
  - Sorts the edges into latitude bands and lists each edge once in every band from its lowest
    latitude minus a margin to its highest plus the margin. The margin is
    `_INDEX_MARGIN_DEG = 4 × EDGE_EPSILON_DEG`.
  - Picks the band count as
    `max(1, min(count // 8, int(3 × count × span / Σ padded edge heights)))`:
    - about eight edges per band;
    - never more bands than keeps the index within `_MAX_BAND_ENTRIES_PER_EDGE = 4` entries per edge.
  - The second limit only binds when edges each span much of the ring's height. More bands would not
    shorten any band there, only copy edges into more of them.
- **`PreparedRing.on_boundary(lat, lon)`:**
  1. Rejects points outside the ring's box plus the margin.
  2. Looks only at the point's band.
  3. Skips edges whose box plus the margin excludes the point.
  4. Applies `point_on_ring`'s arithmetic, unchanged.
- **`PreparedRing.crossings_odd(lat, lon)`:**
  1. Rejects exactly: outside the ring's latitude span, or beyond its longitude span plus the margin.
  2. Applies `ring_contains`'s arithmetic, unchanged, over the edges of the point's band.
- **`PreparedRings.contain`:** a boundary pass over every ring, then a parity pass. This is the same
  structure as `rings_contain`.
- **`prepare(rings)`:** builds a `PreparedRings`. `rings_contain` delegates when it is given one, so
  `contains` and `contains_within` accept either plain or prepared rings.

**`regions/models.py`:** `Region._prepared_rings()` builds the index on first use and keeps it on the
instance, keyed by the identity of the rings object. Assigning new rings, or reloading them, builds a
new index. `contains` and `could_contain` use it.

**`regions/management/commands/bench_containment.py`** (new, with package `__init__.py` files): the
benchmark described above.

**`regions/test_containment_index.py`** (new).

## Why this fixes it
**Less work:**
- The index is built once per `Region` instance and shared by all nine probes of every candidate in
  a poll.
- Each probe looks at one latitude band instead of every edge twice. For evenly spread vertices that
  is about eight edges.
- A ring whose edges each span most of its height gets fewer bands. Its band is then about as long
  as the number of edges crossing that latitude, which is the shape's own minimum.

**Bounded size:**
- An edge lands in at most (its padded height ÷ band height) + 1 bands.
- The band count above therefore keeps the total at most 4 entries per edge, so the index grows
  linearly with the ring.

**Same answers, exactly:**
- **Parity rejects are exact:**
  - Below or above the ring's latitude span, no edge has one end above the point and the other at or
    below it.
  - East of the ring's longitude span (beyond the margin), no crossing lies east of the point.
  - West of it, every crossing counts, and a closed ring always has an even number of crossings.
- **Band lookup misses nothing, for any band count:**
  - An edge that crosses the point's latitude spans that latitude.
  - The band number is non-decreasing in latitude: a floor of a division by a positive step, then
    clamped.
  - So the point's band lies between the edge's first and last band, and the edge is listed there.
  - Each edge is listed at most once per band, so nothing is counted twice.
- **Boundary culls are safe:** `point_on_ring` can only return True within about 1×10⁻⁷° of an edge.
  Every cull leaves 4×10⁻⁷° of slack, far above float error for coordinates within ±540°.
- **Surviving edges behave identically:** each is decided by the same expressions as before, in the
  same order within its ring, so parity and results match exactly.

## Compatibility / deployment notes
- **Nothing external changes:** no API, schema, migration or setting change, and containment answers
  are identical.
- **Where the index lives:** on the `Region` instance, which in the request path lasts one request.
  On the benchmark's rings it holds 51 KiB at 1,500 vertices and 2.4 MiB at 20,000. A `Region`
  pickled after the index was built would carry it in its `__dict__`.
- **In-place mutation:** changing a region's ring lists in place, rather than assigning new rings,
  would not rebuild the index. No code does that today.
- **Plain rings still work:** `geometry.contains`, `contains_within` and `rings_contain` still accept
  plain ring lists. `RegionTraceView` uses them that way.
- **Commit state:** commit `8af6002`, already on `origin/main`, contains the first, uncapped index in
  `geometry.py`, the benchmark command and the first seven tests, but not the `Region` wiring. On
  that commit the index is unused and production still runs the old path. The cap and the wiring are
  in the working tree.

## Remaining risk
- **Measurement scope:** synthetic rings on one Windows machine. Production latency and real boundary
  shapes were not measured.
- **Oversized legacy regions:** rings far above 1,500 points, such as traces stored before H6, stay
  more expensive. At 20,000 vertices a 1,000-candidate poll where every probe misses measured 2.0 s,
  against about 68 s before. Find them with `Region.objects.filter(point_count__gt=1500)`.
- **Still Python:** containment still runs in Python on the request path, over up to 1000 candidates
  per tier. PostGIS remains the structural fix.
