# H6 — Hand-traced region rings have no vertex limit

## Status
FIXED

A hand-traced outline is refused with a 400, before anything is stored, when:
- a ring has more than `REGION_MAX_TRACED_RING_POINTS` points; or
- the outline has more than `REGION_MAX_TRACED_POINTS` in total.

Both limits default to 1500 and are configurable. An oversized list is refused on its length, before
any coordinate in it is parsed. Geometry stored before the limit still reads and tests normally. The
new tests fail against the pre-batch serializer.

While verifying, I found and narrowly fixed a pre-existing bug: the trace endpoint returned 500 for
any user loaded from the database. No deployment was performed.

## Severity
High

## Original problem
Review, page 11 (`regions/serializers.py:58-67`, `TracedRegionSerializer.rings`):
- The outer list was capped at 8 rings and the area was checked. Each ring had `min_length=3` and no
  maximum.
- The only effective bound was `DATA_UPLOAD_MAX_MEMORY_SIZE` (Django's 2.5 MB default), on the order
  of 100,000 vertices.
- A deliberately dense traced zone makes every map poll from that account walk every vertex for
  every candidate (H5). `GET /api/regions/<id>/` then serves the blob back.
- **Suggested fix:**
  - `max_length=2000` per ring;
  - a `REGION_MAX_TRACED_POINTS` setting next to `REGION_MAX_TRACED_AREA_DEG2`;
  - optionally Douglas–Peucker simplification;
  - an explicit `DATA_UPLOAD_MAX_MEMORY_SIZE`.

## Root cause
`validate_rings` checked coordinate range, area and minimum extent, but nothing counted vertices, and
the per-ring `ListField` had no maximum.

## Investigation
- **Pre-batch serializer** (commit `5eaf830`):
  `ListField(child=ListField(child=ListField(child=FloatField(), min_length=2, max_length=2), min_length=3), min_length=1, max_length=8)`.
- **DRF `ListField`** (`rest_framework/fields.py`) enforces `max_length` with a `MaxLengthValidator`.
  Validators run in `run_validation` after `to_internal_value`, which has already validated every
  child. So the review's `max_length=2000` would still parse a 100,000-point ring into 200,000
  floats before refusing it. The tests below measured exactly that count against the old serializer.
- **`RegionTraceView.post`** (`regions/views.py`):
  - validates the payload;
  - requires the user's stored position;
  - checks that the outline contains that position;
  - stores the region with `point_count = sum(len(ring))` and `verified=False`.
- **OSM limit:** `regions/nominatim.py:116` has `MAX_POINTS = 1500`. OpenStreetMap boundaries are
  simplified to at most 1500 points in total before storage, so 1500 is the largest outline the
  zone engine otherwise handles.
- **`DATA_UPLOAD_MAX_MEMORY_SIZE`** is not set anywhere in the project, so Django's 2.5 MB default
  applies.
- **Mobile (`aura-mobile`):** nothing calls `POST /api/regions/trace/`. `services/zoneArea.ts` only
  calls `GET /api/regions/<id>/`, `/api/regions/for-point/` and `/api/regions/search/`. The app's
  "Use my city / district" buttons resolve an existing region. No client change is needed.
- **Pre-existing defect.** `RegionTraceView` passed `user.latitude` and `user.longitude` straight
  into `geometry.contains`.
  - Both are `DecimalField`s, so a user loaded from the database carries `Decimal` values.
  - `geometry.align_lon` computes `middle - lon`, a float minus a `Decimal`, which raises
    `TypeError`.
  - Every real request's user comes from the database, so the endpoint returned 500 for all of them.
  - The line and `align_lon` both arrived in `f9d8ec3` (2026-08-04).
  - Existing tests authenticated a user object whose coordinates were still in-memory floats, so they
    never hit it.
  - The new tests reload the user from the database, as a real request does, and reproduced the
    error: first focused run, `TypeError: unsupported operand type(s) for -: 'float' and
    'decimal.Decimal'`.
  - I fixed it because the accepted-at-the-limit case cannot be verified through the real endpoint
    otherwise.

## Changes made
- **`regions/serializers.py`:**
  - New `_BoundedListField(ListField)` with `max_items`. Its `to_internal_value` raises
    `too_many_items` when `len(data) > max_items`, before any child is validated.
  - `rings` now uses it at every level:
    - At most 8 rings, as before. The message is now `An outline may have at most 8 rings.`
    - Each ring has at least 3 points and at most `REGION_MAX_TRACED_RING_POINTS`, with
      `Each ring may have at most N points.`
    - Each point has exactly 2 numbers. The upper bound is now checked before parsing, with DRF's
      usual `Ensure this field has no more than 2 elements.`
  - `__init__` sets the per-ring limit from settings on the serializer instance's own copy of the
    field. Changing the setting therefore takes effect without re-importing the module.
  - `validate_rings` first refuses a total above `REGION_MAX_TRACED_POINTS`, with
    `That outline has too many points. Keep it to N in total.`
- **`core/settings.py`:** `REGION_MAX_TRACED_RING_POINTS` and `REGION_MAX_TRACED_POINTS`, both
  `config(..., default=1500, cast=int)`, next to `REGION_MAX_TRACED_AREA_DEG2`.
- **`regions/views.py`:** `float(user.latitude), float(user.longitude)` in the containment check,
  for the pre-existing defect above.

**Deliberately not changed:**
- **No Douglas–Peucker simplification.** Refusing is explicit, and silently changing the shape a
  person drew is a product decision.
- **`DATA_UPLOAD_MAX_MEMORY_SIZE` stays at Django's default.** It already bounds the request body.
  The new checks bound what is done with the parsed body.

## Why this fixes it
A traced region can no longer be stored with more than 1500 vertices in total. That is the ceiling
already applied to OpenStreetMap geometry, so a traced zone costs a map poll no more than an OSM
city does. With the H5 index, the worst case at 1500 vertices is 0.18 ms per candidate in the 200-candidate
benchmark.

Refusal costs one `len()` per nesting level, not a parse of the payload.

## Compatibility / deployment notes
- **No migration.** Existing regions, including any traced before this change with more than 1500
  points, are not re-checked or modified. They are still served and still used for containment, as
  the readability test shows.
- **API changes:**
  - A trace over the limit now gets a 400 with a `rings` error. No shipped client sends traces.
  - The wording for more than 8 rings changed from DRF's generic `Ensure this field has no more than
    8 elements.` to `An outline may have at most 8 rings.`
- **New optional settings:** `REGION_MAX_TRACED_RING_POINTS` and `REGION_MAX_TRACED_POINTS` (defaults
  1500). Nothing needs to be set on Railway.
- **Production state:** commit `8af6002`, already on `origin/main`, contains the new serializer but
  not the two settings. On that commit, building the serializer raises `AttributeError`. Before it,
  the endpoint already failed with the `Decimal` `TypeError`. This batch's working tree fixes both.

## Remaining risk
- Traced regions stored before this change may exceed 1500 points and still cost more per poll. Find
  them with `Region.objects.filter(source='user', point_count__gt=1500)`.
- The per-ring and total limits bound work, not shape quality. A 1500-point outline is accepted even
  if a simplified one would do.
- The request body is still bounded only by Django's default `DATA_UPLOAD_MAX_MEMORY_SIZE` (2.5 MB).
