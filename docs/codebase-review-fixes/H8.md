# H8 — Chat sockets reconnect and report their actual state

Status: FIXED. Verified 2026-09-14. Chat reliability batch only; no deployment.

## Problem and implementation

DM and club chat previously created a socket once. A closed connection could leave the header
saying “Reconnecting” without any retry being scheduled.

Both screens now use mobile `hooks/useChatSocket.ts` and `services/chatSocket.ts`.
`ChatSocketConnection` owns one socket, one connection attempt and one retry timer. Its generation
guard discards stale token completions and native events; replacing a connection detaches the old
handlers and closes it before creating the next one.

- Retry delays grow exponentially from a 1-second base to a 30-second maximum, with 50–100%
  jitter. A connection must remain open for 10 seconds before its backoff resets, so flapping
  connections cannot continually retry at the minimum delay.
- A 10-second deadline covers both credential retrieval and the opening handshake. Each retry
  reads the current access token. Error and close events cannot schedule duplicate retries.
- Backgrounding, navigation blur and unmount stop the connection and clear retry, handshake
  and stability timers. Foreground/focus starts a fresh connection. Duplicate active events do
  not create another socket. Route changes dispose of the old connection.
- Status labels distinguish connecting, connected, reconnecting, paused and disconnected.
  Authentication/access close codes 4001/4003/4004 stop automatic retries and show disconnected.
  Existing club-removal navigation remains intact.
- Every successful open triggers history catch-up in both chats. The shared
  `services/chatHistory.ts` follows older-page cursors through the previous history snapshot,
  including gaps longer than 50 messages and a previously empty conversation. Live arrivals
  cannot move this snapshot ahead and cause missed messages to be skipped. Server IDs merge
  overlapping history and live delivery. Stale route/unmount responses are ignored.

DM text delivery is coordinated with [M4](M4.md): REST acknowledgement works while the socket
reconnects. DM history and reads use the contract in [M16](M16.md). Existing image and club
message/proposal sending behavior was not redesigned.

Club history selection in `clubs/views.py` now orders by ID to match its existing exclusive ID
cursor. This is necessary for reliable catch-up when timestamps tie. A backend regression gives
125 messages the same timestamp, inserts a newer message between pages, and proves every
original ID is returned exactly once across the three pages.

## Boundaries and artifacts

Tests simulate native WebSocket and AppState events; backend communicators additionally use real
PostgreSQL and Redis. Physical-device reconnects and deployed multi-worker traffic were not
tested. The transport reacts to native error/close, opening timeouts and foreground lifecycle;
it does not introduce a server heartbeat protocol. The shared test servers were stopped after
verification. The club timestamp-tie issue observed during earlier authentication verification
is now addressed within H8 because reconnect catch-up relies on stable cursor ordering. The
existing club-history validation test and the new multi-page regression both pass.

The task workspace `outputs/chat-reliability/` contains copies of all three reports and the
frontend, backend and PostgreSQL test logs. This change needs the coordinated backend/client
release and migration described in M4/M16.
