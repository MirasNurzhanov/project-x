# L2 — Many modals do not trap screen-reader focus

## Status
FIXED

- **The fix:** every React Native `Modal` in `aura-mobile` now marks a view inside it with
  `accessibilityViewIsModal`, so VoiceOver stays inside the dialog.
- **TermsGate** keeps both of its ways forward, "I agree" and "Sign out", inside the trapped
  view.
- **Modals that would have trapped users:** the create-club interest picker could only be closed
  by an unlabelled backdrop. The club screens' close buttons were unlabelled icons. These now have
  labelled close controls inside the trapped view, plus an Android back handler where one was
  missing.
- **Tests:** a render test covers TermsGate, and a guard test covers every modal. Both fail
  against the old code.
- **Not verified:** the behaviour has not been checked with VoiceOver or TalkBack on a device. No
  deployment or app build was performed.

## Severity
Low

## Original problem
Review, page 35:
- 14 of 19 modals had no `accessibilityViewIsModal`. The review listed `components/TermsGate.tsx`,
  `ReportSheet`, `StoryViewer`, `DirectionsSheet`, `PinNoteEditor`, `DatePickerField`,
  `swifts/SwiftCommentsSheet`, `swifts/SwiftLocationSheet`, `swifts/compose/LocationPickerSheet`,
  `app/(tabs)/map.tsx`, `app/edit-profile.tsx`, `app/create-club.tsx`, `app/clubs/[id].tsx` and
  `app/clubs/[id]/chat.tsx`.
- Without it, VoiceOver and TalkBack read past the dialog into the content behind it.
- TermsGate is the notable case: it is a blocking legal gate that a screen-reader user could
  navigate around.
- **Suggested fix:** `accessibilityViewIsModal` on the modal's backdrop or content view.

## Root cause
React Native's iOS `Modal` does not set `accessibilityViewIsModal` itself. None of
`RCTModalHostView*`, `RCTFabricModalHostViewController` or `RCTModalHostViewComponentView` in
`node_modules/react-native/React` mentions it. A transparent modal is presented over the screen
that opened it, and without the flag VoiceOver can move to elements behind it.

Three of the app's modals set the flag (`LocationDisclosure`, `PermissionPrimer`,
`ZoneTutorialOverlay`); the others did not.

## Investigation
- **Where the modals are:** 18 `<Modal>` elements across 17 files in `app/` and `components/`.
  Three already set the flag; the other 15 are in the 14 files the review named.
- **Close paths:** every modal was checked for a way out that is reachable from *inside* the view
  being trapped, and for Android back handling (`onRequestClose`).
  - **Create-club interest picker:** no close control inside its sheet. Its only exit was an
    unlabelled backdrop `Pressable`, and the `Modal` had no `onRequestClose`. Trapping the sheet
    alone would have stranded a screen-reader user.
  - **Club invite modal and meetup proposal modal:** the close icons had no accessible label. In
    the proposal's map view, the back button was unlabelled too.
  - **Backdrop and sheet as siblings:** in the create-club, invite and proposal modals, the
    backdrop and the sheet were direct children of `Modal`. There was no single view to mark.
- **Android:** a React Native `Modal` is its own dialog window, so TalkBack is already confined to
  it. `accessibilityViewIsModal` is iOS-only. On Android the relevant part is that the back button
  closes the modal.
- **Existing pattern:** `ZoneTutorialOverlay` and `LocationDisclosure` put the flag on the root
  view inside the `Modal`. `services/__tests__/zoneTutorialOverlay.test.tsx` asserts it is inside
  the `Modal` rather than beside it.

## Changes made
The flag is placed on the outermost view inside each modal, so every control the modal owns
(backdrop included) is inside the trapped region.

| Modal | Trapped view | Way out inside it | Android back |
|---|---|---|---|
| `components/TermsGate.tsx` | root `View` | "I agree to the terms", "Sign out instead" (and the three document links) | intentionally a no-op; Sign out is the exit |
| `components/ReportSheet.tsx` | root `View` | backdrop labelled "Close", sheet actions | `handleClose` (unchanged) |
| `components/StoryViewer.tsx` | `KeyboardAvoidingView` around the viewer | labelled close button | `onClose` (unchanged) |
| `components/DirectionsSheet.tsx` | `DirectionsContent` root `View` | backdrop "Close", close button | `onClose` (unchanged) |
| `components/PinNoteEditor.tsx` | `PinNoteForm` root `KeyboardAvoidingView` | backdrop "Close", Cancel | `onClose` (unchanged) |
| `components/DatePickerField.tsx` | overlay `View` | Cancel, Done | **added** `onRequestClose={() => setOpen(false)}` |
| `components/swifts/SwiftCommentsSheet.tsx` | `CommentsBody` root `KeyboardAvoidingView` | labelled close | `onClose` (unchanged) |
| `components/swifts/SwiftLocationSheet.tsx` | root `View` | labelled close | `onClose` (unchanged) |
| `components/swifts/compose/LocationPickerSheet.tsx` | `PickerBody` root `View` | Cancel | `onCancel` (unchanged) |
| Story composer (`CreateStoryModal`, was in `app/(tabs)/map.tsx`, now `components/map/CreateStoryModal.tsx` after L5) | `KeyboardAvoidingView` | header button labelled "Close" | `onClose` (unchanged) |
| `app/edit-profile.tsx`, profession and nationality pickers | `modalRoot` `View` (both) | Cancel, Done | `onCancel` (unchanged) |
| `app/create-club.tsx`, interest picker | **new** `View style={{ flex: 1 }}` wrapping backdrop and sheet | backdrop now a button labelled "Close" | **added** `onRequestClose={onDismiss}` |
| `app/clubs/[id].tsx`, invite modal | **new** wrapper around backdrop and sheet | backdrop and header close both labelled "Close" | `onDismiss` (unchanged) |
| `app/clubs/[id]/chat.tsx`, meetup proposal | the fragment became a wrapper `View`; the map-picker root is trapped too | backdrop and header close labelled "Close"; map back button labelled "Back to the proposal" | unchanged (back to form or dismiss) |

**Why the wrappers are layout-neutral.** The modal's backdrop is `flex: 1` and the sheet follows it
in a column. A `flex: 1` wrapper holding the same two children in the same order lays out
identically.

**Two structural edits were scripted.** Wrapping and re-indenting the create-club and invite
modals was done with `scratchpad/l2_wrap_modals.js`. It checks each anchor line (the `Modal`, the
backdrop, the sheet's closing tag) before changing anything.

## Why this fixes it
- **Focus stays in the dialog.** Each modal marks one view as the accessibility modal, so VoiceOver
  ignores the screen behind a transparent dialog.
- **No trap without a way out.** Every trapped view contains a labelled close or action, and
  Android back closes each modal except TermsGate. TermsGate's exits are "I agree" and "Sign out",
  both inside it.

## Tests added or changed
`aura-mobile/services/__tests__/termsGate.test.tsx` (new, 5 tests), rendering TermsGate with its
theme, insets and terms service mocked:
- A view with `accessibilityViewIsModal` exists inside the `Modal`. It contains "I agree to the
  terms", "Sign out instead" and the links to all three documents.
- Android back (`onRequestClose`) calls neither callback, and the gate stays up.
- "Sign out instead" calls `onSignOut`.
- "I agree" records acceptance and calls `onAccepted`.
- Nothing renders while hidden.

`aura-mobile/services/__tests__/modalAccessibility.test.ts` (new, 35 tests):
- It scans every `.tsx` file under `app/` and `components/` that contains `<Modal`, currently 17.
- It confirms the scan finds known modals, including TermsGate, ReportSheet, StoryViewer,
  create-club and the club invite modal.
- For each file, `accessibilityViewIsModal` must appear at least as many times as `<Modal`.
- For each file, any backdrop `Pressable` with an `onPress` written between a `Modal`'s tags must
  have an `accessibilityLabel`.

## Compatibility / deployment notes
- **Behaviour change:** only for assistive technology, plus Android back now closing the date
  picker and the create-club interest picker (previously it did nothing).
- **Screen-reader wording:** the new labels are "Close" and "Back to the proposal".
- **Layout:** no visual change is intended. The two wrapper views are `flex: 1` containers around
  the same children.

## Remaining risk
- **No device check.** Nothing was checked with VoiceOver or TalkBack on a device.
  `accessibilityViewIsModal` hides only the marked view's siblings. Placing it on the outermost
  view inside each `Modal` is the established pattern, but its effect on each presentation style
  was not observed.
- **The guard test is a count.** It would miss a modal whose flag lives in a different component
  from the `<Modal>`, and it would be fooled by the word appearing in a comment. The TermsGate
  render test is the behavioural one.
- **Remaining unlabelled controls:**
  - Some are not close paths, such as the clear-search icons in the club screens.
  - The story composer's backdrop is unlabelled, but a labelled "Close" button sits beside it
    inside the trapped view.
