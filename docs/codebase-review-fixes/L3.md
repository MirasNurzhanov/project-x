# L3 — Module-level map callback registries are never unregistered

## Status
FIXED

The map registers two module-level callbacks: its refresh, and its meetup remover. Both
registrations now return an unregister function, which `useMapData`'s effects run on cleanup. Once
the map unmounts, a trigger from another screen makes no request and updates no state.

Each unregister clears its slot only while the slot still holds that same callback. A stale cleanup
therefore cannot remove a newer map's registration.

Tests cover the registry and the real hook, and fail against the old code. No deployment or app
build was performed.

## Severity
Low

## Original problem
Review, page 35 (`hooks/useMapData.ts:354-362`, `services/nearbyRefresh.ts:1-2`):
- The map calls `registerNearbyRefresh(tick)` and `registerMeetupRemove(…)` in effects that return
  no cleanup. `services/nearbyRefresh.ts` holds the callbacks in module-level `let _refresh` and
  `let _removeMeetup`.
- **What goes wrong:** when the map unmounts, the stale `tick` closure stays installed. Another
  screen calling `triggerNearbyRefresh()` afterwards runs an API call and a state update against
  an unmounted component.
- **What does not:** remounting overwrites the slot, so closures do not accumulate.
- **Suggested fix:** `return () => registerNearbyRefresh(null)` from the effect.

## Root cause
The registry had no way to take a callback back, and the registering effects returned nothing.

## Investigation
- **Callers:**
  - `app/(tabs)/chat.tsx` calls `triggerNearbyRefresh()` after a friendship action (lines 874 and
    1007).
  - `app/clubs/[id]/chat.tsx` calls `removeMeetupFromMap(id)`.
  - `hooks/useMapData.ts` is the only registrant. It registers `tick` (re-registered whenever
    `tick` changes identity), and a meetup remover that updates `clubMeetups` state, registered
    once.
- **What `tick` does:** `reportLocation(...)` (a location write) and `fetchMapData()` (the
  `/api/map/…` fetch plus state updates). A stale `tick` is therefore both a network call and a
  state write.
- **Why the review's `null` version is not enough:** clearing the slot to `null` on cleanup
  unconditionally would break the case where the cleanup runs after a newer registration. That
  happens when `tick` changes identity, or when two map instances overlap during navigation.
- **Existing test:** `services/__tests__/mapGhostPrivacy.test.tsx` mocks the registry, with
  functions returning `undefined`, to drive `useMapData`. An effect returning `undefined` is still
  valid, so that test needs no change.
- **Related, not changed:** `services/profileRefresh.ts` has the same shape: the profile tab's
  `registerProfileRefresh` in `app/(tabs)/profile.tsx:180` has no cleanup either. It is not a map
  registry and is outside this finding.

## Changes made
- **`services/nearbyRefresh.ts`:**
  - `registerNearbyRefresh(fn)` and `registerMeetupRemove(fn)` now return `() => void`.
  - The returned function sets the slot back to `null` only if the slot still holds `fn`.
  - The trigger functions are unchanged.
  - A module comment explains the ownership rule.
- **`hooks/useMapData.ts`:**
  - `useEffect(() => registerNearbyRefresh(tick), [tick]);`
  - `useEffect(() => registerMeetupRemove((id) => { … }), []);`
  - Each effect returns the unregister as its cleanup.

## Why this fixes it
- **Unmount:** React runs each effect's cleanup when the map unmounts, and before re-running the
  refresh effect for a new `tick`. The slot is then empty, so `triggerNearbyRefresh()` and
  `removeMeetupFromMap()` do nothing.
- **Overlapping maps:** the identity check makes the order of mounts and cleanups safe. A newer
  map's registration survives an older map's late cleanup.
- **Requests already in flight:** a request started before unmount still finishes. React ignores a
  state update on an unmounted component and does not warn (React 19.1 here). What this finding
  describes, and what is now prevented, is new work started by triggers after unmount.

## Tests added or changed
`aura-mobile/services/__tests__/nearbyRefresh.test.tsx` (new, 3 tests):
- **Registry:** for both registries, an older registration's unregister leaves a newer callback
  installed, and the newer one's unregister clears it.
- **The real `useMapData` hook**, with API, discovery, location, stories and privacy mocked:
  - While mounted, `triggerNearbyRefresh()` fetches once and `removeMeetupFromMap(30)` removes the
    meetup.
  - After unmount, both triggers cause no `fetchMapNearby` call and no `reportLocation` call.
- **Two mounted instances:** after the older one unmounts, a trigger still reaches the newer one.
