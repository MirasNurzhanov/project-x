# L4 — AuthProvider value/functions are recreated unnecessarily and startup has a fixed delay

## Status
FIXED

- **Stable functions:** `AuthProvider`'s four functions keep one identity for the life of the
  provider.
- **Stable context value:** the value is memoised, so it changes only when `isAuthenticated`,
  `isLoading` or `isSigningOut` changes.
- **No fixed startup wait:** the 2.5 s wait on every cold start is gone. Loading ends as soon as the
  stored token has been read.
- **Unchanged:** token bootstrap, sign-in, forced logout and sign-out confirmation behave as before.

Tests fail against the old code. No deployment or app build was performed, and cold-start time was
not measured on a device.

## Severity
Low

## Original problem
Review, page 36 (`context/AuthContext.tsx:162-168`):
- The context value object and all four functions were created inline. Every `useAuth()` consumer
  re-rendered whenever the provider did, and `useAuth` is consumed near the root.
- **Suggested fix:** `useCallback` for the functions and `useMemo` for the value.
- **Related:** a hard `setTimeout(resolve, 2500)` on cold start meant every launch waited 2.5 s on
  the splash, even when the token read returned immediately.

## Root cause
- **Value and functions:** they were declared inline in the component body, so each provider render
  produced new identities.
- **Startup delay:** bootstrap waited on `Promise.all([getAccessToken(), 2.5 s timer])` rather than
  on the token read alone.

## Investigation
- **Consumers:**

  | File | Reads |
  |---|---|
  | `app/_layout.tsx` (`AppShell`) | `isLoading`, `isAuthenticated`, `logout` |
  | `app/index.tsx` | `isAuthenticated`, `isLoading` |
  | `app/login.tsx` | `login` |
  | `app/social-birthday.tsx` | `confirmLogout` |
  | `components/SocialAuthButtons.tsx` | `completeSocialSignIn` |
  | `app/(tabs)/settings.tsx` | `logout`, `confirmLogout`, `isSigningOut` |

- **Where the provider sits:** inside `AppThemeProvider`, `ScrollNavProvider` and
  `NavStyleProvider`. A state change in any of those re-rendered the provider, and with it every
  consumer, even though no auth state had changed.
- **The failure handler:** the mount effect registers `setOnAuthFailure(() => { logout(); })`,
  closing over the first render's `logout`. That already worked, because `logout` touches only
  state setters and a ref.
- **React Compiler:** it is enabled (`app.json` `experiments.reactCompiler: true`) and may already
  memoise much of this in built apps. Existing comments in this file note the compiler bails out on
  some constructs. Jest does not show what the compiler does with this component, so relying on it
  was not verifiable here.
- **Where the 2.5 s wait came from:** it arrived in `0e19224` (2026-05-20), "Add AuraLoader splash
  animation, pulse particles".
  - `components/ApproxLoader.tsx` animates with `withRepeat(…, -1)`: an endless pulse with no
    sequence that needs to finish.
  - `AppShell` shows the loader only while `isLoading` is true, and `app/index.tsx` waits for the
    same flag.
  - So the timer only held launches on the loader after the answer was already in.
- **The token read:** `getAccessToken()` is `AsyncStorage.getItem('access_token')`. Its behaviour,
  including the absence of error handling, is unchanged.

## Changes made
`context/AuthContext.tsx`:
- **`logout`:** `useCallback(async () => { … }, [])`, with its body unchanged, including the
  re-entrancy ref, the flag ordering, the teardown and the navigation.
- **`login`:** `useCallback(…, [])`.
- **`completeSocialSignIn`:** `useCallback(…, [])`.
- **`confirmLogout`:** `useCallback(…, [logout])`.
- **Declaration order:** the callbacks are declared before the mount effect, whose dependency list
  is now `[logout]`. `logout` is stable, so the effect still runs once.
- **Bootstrap:** now `getAccessToken().then(token => …)`. The body is the same as before (mark
  onboarding seen when a token exists, set the flags), without the timer.
- **Context value:** `useMemo` over the three flags and four functions.
- **Comments:** they explain why the functions are stable despite React Compiler, and why the wait
  was removed.

## Why this fixes it
- **Unrelated re-renders:** when the provider re-renders for a reason unrelated to auth, such as a
  parent provider's state change, consumers receive the same value object. A context consumer
  re-renders only when that value changes.
- **Real auth changes:** when a flag does change, the value changes and consumers update, which is
  required. The four functions keep their identity even then, so they are safe in dependency arrays
  and memoised children.
- **Startup:** loading ends when `getAccessToken()` resolves, with no artificial minimum.

## Tests added or changed
`aura-mobile/services/__tests__/authContext.test.tsx` (new, 7 tests). Router, api, auth,
onboarding and sign-out services are mocked.

**Bootstrap:**
- **No fixed wait:** with fake timers that are never advanced, `isLoading` is true until the token
  read resolves and false immediately after. `isAuthenticated` is true, and onboarding is marked
  seen.
- **No stored token:** loading ends, the user is signed out, and onboarding is not marked.

**Context value:**
- **Same object when nothing changed:** re-rendering the provider twice from its parent, with no
  state change, keeps the identical value object.
- **Same functions when flags change:** after `login` flips `isAuthenticated`, the value changes but
  `login`, `logout`, `confirmLogout` and `completeSocialSignIn` are the same functions.

**Session behaviour, unchanged:**
- **Sign-in:** `login` passes the agreement flag to `loginRequest` and replaces to `/(tabs)/map`.
- **Forced logout:** the handler registered with `setOnAuthFailure` runs `performSignOut` once,
  signs out, clears `isSigningOut` and replaces to `/welcome`.
- **Confirmed sign-out:** `confirmLogout` shows the alert. Pressing "Sign out" twice still signs out
  once.

## Compatibility / deployment notes
- **Faster cold start:** cold start no longer holds the loader for 2.5 s. On a fast device the
  loader may now show only briefly before routing.
- **Unchanged:** sign-in, social sign-in, forced logout, sign-out and the Terms/onboarding routing
  that depends on `isLoading`.

## Remaining risk
- **Loader flash:** a very short loader appearance might read as a flash. If a minimum display is
  wanted for branding, it should be a deliberate design choice, not a delay on the auth answer.
- **Not measured:** cold-start time and render counts in a built app with React Compiler were not
  measured.
- **One shared context:** consumers that read only a function still re-render when any flag
  changes. Splitting the context would narrow that, but was not part of this finding.
