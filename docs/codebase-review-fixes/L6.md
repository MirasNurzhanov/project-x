# L6 — Frontend BASE_URL is hardcoded to production

## Status
FIXED

The mobile app now reads its API address from `EXPO_PUBLIC_API_URL`:
- Set per build, in `.env.local` for local development or in an `eas.json` build profile for EAS
  builds.
- When unset, it defaults to production.
- Changing backends no longer needs a tracked source edit.
- A release build refuses plain `http` and local or private-network hosts, so a development address
  cannot quietly ship.
- The production EAS profile is pinned to the production API.

21 new tests pass, and three deliberate breakages of the fix each make them fail. No EAS or device
build was run.

## Severity
Low

## Original problem
Review, page 36 (`services/api.ts:6`, `export const BASE_URL = 'https://project-x-production-3261.up.railway.app'`):
- Pointing the app at a local or staging backend meant editing a tracked source file. That is easy to
  commit by accident and easy to forget to revert.
- Expo supports `EXPO_PUBLIC_API_URL`, and `eas.json` already exists as the natural place to set it
  per build profile.
- **Suggested fix:**
  `export const BASE_URL = process.env.EXPO_PUBLIC_API_URL ?? 'https://project-x-production-3261.up.railway.app';`

## Root cause
The backend address was a single string constant, with no build-time or environment hook.

## Investigation
- **Consumers of `BASE_URL`:**
  - `services/api.ts`: the axios instance and token refresh.
  - `services/auth.ts`, `services/signOut.ts`, `services/socialAuth.ts` and `app/register.tsx`:
    requests made before a session exists.
  - `services/swiftUpload.ts`: the upload request.
  - `services/terms.ts`: legal page URLs.
  - `hooks/useChatSocket.ts`: derives the socket URL by swapping `http` for `ws`, so `https` becomes
    `wss`.
  - Tests mock `../api` with `example.test` addresses.
- **Existing convention:** `services/routing.ts` already reads `EXPO_PUBLIC_ROUTING_*`.
  - It uses direct `process.env.NAME` access, because Expo only inlines public variables at bundle
    time when written that way.
  - It validates with a narrow pattern, because React Native 0.81's `URL` is too permissive to trust.
- **Expo SDK 54** (`expo ~54.0.37`):
  - Expo CLI loads `.env` and `.env.local` files and inlines `EXPO_PUBLIC_*` values into the bundle.
  - An `eas.json` build profile's `env` values are set in that build's environment.
  - `expo-updates` is not installed, so there is no over-the-air update path that could carry a
    different value.
- **`.gitignore`:** covers `.env*.local` but not `.env`. There is no `.easignore`, so EAS uploads
  whatever git does not ignore.
- **`eas.json`:** has `development` (dev client, internal), `preview` (internal) and `production`
  (auto-increment) profiles. None of them set an environment variable.
- **No staging backend address** exists in either repository. `docs/scaling-railway.md` describes
  creating a staging environment but gives no URL, so none is committed here.
- **The suggested `??` fallback** would accept an empty string (`EXPO_PUBLIC_API_URL=` gives relative
  requests) and any value at all, including `http://localhost:8000`, in a store build. That is why
  the value is validated.

## Changes made
All in `aura-mobile`.

**`services/apiUrl.ts` (new):**
- **`PRODUCTION_API_URL`:** the existing production address.
- **`resolveApiUrl(raw, isDevelopment)`:**
  - An unset or blank value gives production.
  - It accepts only `http(s)://host[:port][/path]`: a DNS name or IPv4 host, a port from 1 to 65535,
    and no credentials, query or fragment. Scheme and host are lowercased and trailing slashes
    removed. Anything else throws an error naming `EXPO_PUBLIC_API_URL`.
  - When `isDevelopment` is false (a release build), it also throws for `http`, and for hosts
    `localhost`, `*.localhost`, `*.local`, `0.x`, `10.x`, `127.x`, `169.254.x`, `172.16–31.x` and
    `192.168.x`.
- **`API_URL = resolveApiUrl(process.env.EXPO_PUBLIC_API_URL, __DEV__)`:** uses direct property
  access so Expo inlines the value.

**`services/api.ts`:** `export const BASE_URL = API_URL;`. The export name is unchanged, so every
consumer and every existing test mock is untouched.

**`eas.json`:** the `production` profile sets `env.EXPO_PUBLIC_API_URL` to the production address.
Store builds therefore do not depend on the fallback. As I understand Expo's documented precedence, a
variable already set in the build environment is not overridden by a `.env` file, so a stray `.env`
cannot redirect them. This project has no build that proves it. `development` and `preview` stay
unset, meaning production, until a staging backend exists.

**`README.md`:** a "Which backend a build talks to" section covering:
- `.env.local` for local servers, including the Android emulator's `10.0.2.2`;
- the per-profile `env` in `eas.json`;
- restarting Metro with `--clear`;
- why local addresses belong in `.env.local`, not `.env`.

## Why this fixes it
Pointing a build elsewhere is now configuration:
- **Local development:** a gitignored `.env.local`.
- **EAS builds:** a build profile in `eas.json`.

No source edit is involved, so nothing is left to revert. The committed default is production, and
the production profile names it explicitly. A local or unencrypted address in a release build stops
the app at launch rather than shipping silently.

## Tests added or changed
`services/__tests__/apiUrl.test.ts` (new, 21 tests including parameterised cases):
- **Default:** an unset or blank value resolves to production in both build types. The production
  address itself passes the release checks.
- **Staging:** an https address with an uppercase host, trailing slash, port or path is accepted in a
  release build and normalised.
- **Development:** `http://192.168.1.20:8000`, `http://10.0.2.2:8000/` and `http://localhost:8000`
  are accepted.
- **Release refusals (8 cases):** `http://api.example.test`, `http://192.168.1.20:8000`,
  `https://localhost:8000`, `https://127.0.0.1`, `https://10.0.2.2:8000`, `https://172.20.0.5`,
  `https://192.168.1.20` and `https://laptop.local` are refused.
- **Malformed values (8 cases), refused in both build types:**
  - no scheme;
  - `ftp:`;
  - `user:secret@` credentials;
  - a query;
  - a fragment;
  - a space;
  - an empty host label;
  - port 70000.
- **Module load:** `API_URL` follows `EXPO_PUBLIC_API_URL` (unset gives production; a staging value
  with a trailing slash gives the normalised address). Loading uses `jest.isolateModules`, the same
  pattern as `routing.test.ts`.
- **Build profiles:** the `production` profile in `eas.json` is pinned to `PRODUCTION_API_URL`, and
  every profile that sets `EXPO_PUBLIC_API_URL` passes the release checks.

## Compatibility / deployment notes
- **No behaviour change yet:** every existing build, and every profile without the variable, still
  talks to production.
- **Baked in at build time:** the value is part of the JavaScript bundle. Changing it needs
  `npx expo start --clear` locally, or a new build.
- **Launch failure is deliberate:** a release build given an invalid, unencrypted or local address
  throws when `services/api.ts` loads, so the app fails at launch. This is meant to surface in
  internal testing.
- **When a staging backend exists:** add
  `"env": { "EXPO_PUBLIC_API_URL": "https://<staging-host>" }` to the `preview` profile.
- **EAS dashboard:** EAS environment variables configured there, if any, could also set this
  variable. They are not visible from the repository.

## Remaining risk
- **Checked at launch, not at build time:** a misconfigured preview build still builds and only fails
  when opened.
- **`.env` is not gitignored:** a committed `.env` holding a development address would reach
  development and preview builds. Production is pinned in `eas.json`, and the release guard rejects
  local hosts.
- **No real builds run:** nothing was verified in an EAS build or on a device. The inlining behaviour
  is the same mechanism `services/routing.ts` already relies on.
