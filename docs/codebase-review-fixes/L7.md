# L7 — Google client API keys are committed and their restrictions require verification

## Status
NEEDS EXTERNAL ACTION

**What was verified here:** the repository side.
- The three committed Google API keys are Android and iOS client keys. They ship inside the app
  binary by design and are not server secrets.
- Neither repository contains a private credential, in the current tree or anywhere in git history.

**What was not verified:** whether each key is actually restricted. That can only be checked in the
Google Cloud / Firebase console, which I have no access to.

No key value is reproduced in this report. Keys are identified only by where they live.

## Severity
Low

## Original problem
Review, page 36:
- **What it cited:** `app.json:13` (`googleMapsApiKey`) and `app.json:34`, described as the Firebase
  `apiKey`.
- **What it said:**
  - Both are client-side keys that necessarily ship in the app bundle, so committing them is not in
    itself a leak.
  - The Maps key in particular is only safe if restricted in Google Cloud: by Android package name
    plus SHA-1 certificate fingerprint, by iOS bundle ID, and by API.
  - An unrestricted Maps key extracted from a public bundle is a billing-abuse vector.
  - Verification is outside the repository. If either key is unrestricted, restrict it and rotate it.

**One correction to the citation.** `app.json:34` is the Android **Maps** key. The Firebase key
lives in `google-services.json`. There are three keys, not two.

## Root cause
The native Google Maps SDKs and Firebase read their API keys from the app's own configuration. Expo
writes them into the Android manifest and resources and the iOS `Info.plist`, so the key has to be
in the build. A key that ships to devices can only be protected by restrictions set in Google Cloud,
and nothing in the repository can enforce or show those restrictions.

## Required restrictions (to verify or apply in the console)
Where to look: Google Cloud console → APIs & Services → Credentials, then each key. Check the Firebase
project `aura-96d48` and the project the OAuth client IDs belong to.

| Key | Application restriction | API restriction |
|---|---|---|
| 1 — iOS Maps (`app.json` `ios.config.googleMapsApiKey`) | **iOS apps**, bundle ID `com.arcanix.aura` | **Maps SDK for iOS** only |
| 2 — Android Maps (`app.json` `android.config.googleMaps.apiKey`) | **Android apps**, package `com.arcanix.aura` plus the SHA-1 of every signing certificate listed below | **Maps SDK for Android** only |
| 3 — Firebase Android (`google-services.json`) | **Android apps**, package `com.arcanix.aura` plus the same SHA-1 fingerprints | Only the APIs the app's Firebase features use (see below) |

**SHA-1 fingerprints to register for keys 2 and 3**, one for every certificate that signs a build
people install:
- **Google Play app signing key.** Play Console → the app → App signing → "App signing key
  certificate". This signs store installs.
- **The EAS keystore** (`eas credentials -p android`). This signs internal, preview and development
  builds, and is the upload key.
- **Any keystore used for local `expo run:android` builds**, such as the Android debug keystore, if
  those builds are expected to show maps.

**API list for key 3.** Push goes through FCM, which typically needs the Firebase Installations API
and the FCM Registration / Cloud Messaging APIs. Before restricting, read the key's per-API usage in
the console, and keep only what it actually calls. Firebase's auto-created keys can depend on more.

**Also check:**
- **Budget and quotas:** a budget alert, and per-API quotas on the Maps SDKs, in whichever project
  bills them.
- **The Google Sign-In OAuth clients** (not API keys, but related):
  - the Android OAuth client must list package `com.arcanix.aura` with the same release and debug
    SHA-1s;
  - the iOS OAuth client must use bundle ID `com.arcanix.aura`.

**If a key turns out to be unrestricted:**
1. Restrict it now.
2. Review its usage for traffic that did not come from the app.
3. If there is abuse, create a restricted replacement key and ship it in a new build: update
   `app.json`, or download a fresh `google-services.json`.
4. Delete the old key only once builds that embed it are no longer supported. Deleting it earlier
   breaks maps and push in installed apps.

The old value stays in git history permanently, so rotation, not deletion from the repository, is
what neutralises it.

## Compatibility / deployment notes
- **Before restricting keys 2 and 3 by SHA-1,** add every fingerprint listed above. A build signed by
  an unlisted certificate loses maps (a blank map and an authorization error in the device logs) and
  Firebase push registration.
- **After changing restrictions,** check a Play Store build, an EAS internal build and a development
  build.
- **Rotating a key needs a new app build.** The old key has to stay valid until installed builds that
  embed it are retired.

## Remaining risk
- Until the console is checked, any unrestricted key can be extracted from the public app and used
  for billable Google Maps Platform requests, or to exercise Firebase APIs, against this project.
- The current key values are in git history permanently. Restriction and, if needed, rotation are
  the remedy.
