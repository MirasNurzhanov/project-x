# L8 — Blocked-author subquery is duplicated in feed visibility query

## Status
FIXED

The Swift feed gate `watchable_q` now compiles to one correlated `friends_blockeduser` subquery
instead of three. The rows it selects are unchanged: a 108-combination matrix agrees with the
Python gate `can_watch`, and the existing visibility tests pass. The old code fails the new
SQL-shape test. A mutation that removes the remaining block clause fails three tests. No deployment
was performed.

## Severity
Low

## Original problem
Review, page 37 (`swifts/visibility.py:110,126`):
- `watchable_q` was `live_q() & audience_q(viewer) & ~_blocked_author_q(viewer)`.
- `audience_q` already embeds `unblocked = ~_blocked_author_q(viewer)` in its public and friends
  branches.
- The review notes the result is correct (the same predicate twice), but the planner sees duplicate
  correlated `EXISTS` subqueries on `friends_blockeduser` in the hottest feed query.
- Suggested resolution: keep the guarantee and hoist the shared clause in `watchable_q`.

## Root cause
The two functions are each documented as safe on their own:
- `audience_q` applies the block check inside the two branches that admit other people's rows. These
  are PUBLIC Swifts of a private account seen by approved viewers, and FRIENDS Swifts.
- `watchable_q` adds its own top-level block check so that it does not depend on `audience_q`.

Composing them put one predicate into the SQL three times: public branch, friends branch and top
level. The review counted two because the two inner copies come from one Python variable.

## Investigation
- `_blocked_author_q(viewer)` is `Q(Exists(BlockedUser ... blocker=viewer, blocked=author OR
  blocked=viewer, blocker=author))`. `EXISTS` is always TRUE or FALSE in SQL, never NULL.
- `audience_q` is called only from `swifts/visibility.py` (`watchable_q`) and the new test. It stays
  public and unchanged.
- `can_watch`, the Python counterpart used for single objects, returns False on a block before
  looking at the audience. It is not changed.
- **SQL shape before the change**, from `scratchpad/l8_query_shape.py` (migrated in-memory SQLite,
  `core.test_settings`, `watchable(viewer).query`): 3 `friends_blockeduser` references, 6
  `EXISTS`, 3459 characters of SQL. `EXPLAIN QUERY PLAN` had 38 rows and 6 correlated scalar
  subqueries, 3 of them on `friends_blockeduser`.

## Changes made
`swifts/visibility.py`:
- **New private `_audience_q(viewer, unblocked)`:** the previous body of `audience_q`, with the block
  clause for the approved-viewer branches passed in.
- **`audience_q(viewer)`:** now returns `_audience_q(viewer, ~_blocked_author_q(viewer))`. Its rows
  and SQL are unchanged, and it still has both block clauses.
- **`watchable_q(viewer)`:** now returns
  `live_q() & _audience_q(viewer, Q()) & ~_blocked_author_q(viewer)`. The docstring records why the
  inner copies are redundant. Django drops an empty `Q()` when it is combined with `&`, so the inner
  branches compile without the clause.

## Why this fixes it
With `B` = "a block exists between viewer and author":
- **Old:** `L ∧ (own ∨ (G ∧ ((P ∧ (N ∨ ((F ∨ C) ∧ ¬B))) ∨ (V ∧ F ∧ ¬B)))) ∧ ¬B`
- **New:** the same expression with the inner `¬B` replaced by TRUE, keeping the outer `∧ ¬B`.

The two agree for every row:
- If `B` is TRUE, both are FALSE because of the outer conjunct.
- If `B` is FALSE, the inner `¬B` is TRUE in both.

This also holds under SQL three-valued logic, because `¬B` is never UNKNOWN and `X AND FALSE` is
FALSE for any `X`. The block guarantee is still enforced in `watchable_q` itself, which the review
asked to keep.

**SQL shape after**, same script and database:

| | Before | After |
|---|---|---|
| `friends_blockeduser` references | 3 | 1 |
| `EXISTS` subqueries | 6 | 4 |
| SQL length (characters) | 3459 | 2971 |
| `EXPLAIN QUERY PLAN` rows | 38 | 26 |
| Correlated scalar subqueries (on `friends_blockeduser`) | 6 (3) | 4 (1) |

## Compatibility / deployment notes
- No API, schema, migration or setting change. The feed returns the same rows with one fewer pair of
  correlated subqueries.

## Remaining risk
- The plan and timing were measured on SQLite only. On PostgreSQL the saving is two
  unique-index lookups per candidate row, and its size on real data was not measured.
- If a future branch added to `_audience_q` admits other people's rows, it relies on `watchable_q`'s
  top-level block clause. The matrix test and the existing blocking test fail if that clause is
  removed.
