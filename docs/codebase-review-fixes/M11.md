# M11 — Deployment security settings are missing and forwarded proxy headers are trusted too broadly

## Status
NEEDS EXTERNAL ACTION

All repository-side work is done and verified by tests. Django no longer reads forwarded headers
itself; the trusted-proxy boundary is uvicorn's, fed by `FORWARDED_ALLOW_IPS`. M11 is **not** marked
FIXED, because two things cannot be proven from this repository:
1. The Railway edge proxy's address range. It has to be verified with Railway and set as
   `FORWARDED_ALLOW_IPS`.
2. Post-deployment behaviour. See *Required post-deploy verification*; results have not been
   provided yet.

Status history:
- First pass (2026-09-13): PARTIALLY FIXED, because Django still trusted a raw `X-Forwarded-Proto`.
- This pass (2026-09-13): proxy trust moved to uvicorn. Remaining items are external only.

## Severity
Medium

## Original problem
Review, page 26:
- `manage.py check --deploy` reported `security.W004`, `W008`, `W012` and `W016`.
- `ALLOWED_HOSTS = ['*']`.
- `USE_X_FORWARDED_HOST = True`.
- `SECURE_PROXY_SSL_HEADER` was trusted unconditionally.
- uvicorn ran with `--forwarded-allow-ips="*"`.

Consequences:
- The admin session cookie could travel over plaintext.
- No HSTS protected against downgrade.
- Any peer that reached the process could assert `X-Forwarded-Proto: https`.
- Absolute URLs could take an attacker-supplied host.

## Root cause
At `HEAD` (`5eaf830`):
- `core/settings.py:13`: `ALLOWED_HOSTS = ['*']`.
- `core/settings.py:377-378`: `USE_X_FORWARDED_HOST = True` and
  `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')`.
- No `SECURE_SSL_REDIRECT`, `SECURE_HSTS_*`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`,
  `SESSION_COOKIE_SAMESITE` or `SECURE_REFERRER_POLICY` anywhere.
- `Procfile:2`: `uvicorn … --proxy-headers --forwarded-allow-ips="*"`.

## Trust models

### Original (`HEAD`)
```
any peer ──X-Forwarded-Proto──▶ uvicorn (--forwarded-allow-ips="*": trusts every peer)
                              └▶ Django SECURE_PROXY_SSL_HEADER (reads the raw header again, from anyone)
                                 + USE_X_FORWARDED_HOST=True (Host taken from a raw header)
```

### After the first M11 pass (uncommitted, superseded)
```
any peer ──X-Forwarded-Proto──▶ uvicorn (FORWARDED_ALLOW_IPS unset → default 127.0.0.1 → trusts no remote peer)
                              └▶ Django TRUST_PROXY_SSL_HEADER=True in production
                                 → SECURE_PROXY_SSL_HEADER → still reads the raw header from ANY peer
```
uvicorn had stopped trusting everyone, but Django still went around it: `HttpRequest.scheme`
(`django/http/request.py:307-320`) returns `https` whenever the raw header says so, whatever the
connecting peer. `USE_X_FORWARDED_HOST` was also still switchable on from the environment.

### New (this pass)
```
Railway edge proxy (peer address in FORWARDED_ALLOW_IPS)
   │ X-Forwarded-Proto / X-Forwarded-For
   ▼
uvicorn ProxyHeadersMiddleware ── peer in FORWARDED_ALLOW_IPS? ── no ──▶ headers ignored, scope scheme stays "http"
   │ yes
   ▼ scope["scheme"] = "https", scope["client"] = real client
Django ASGIRequest._get_scheme() → scope["scheme"]      (SECURE_PROXY_SSL_HEADER = None)
   ▼
SecurityMiddleware redirect / HSTS, CSRF same-origin check, secure cookies, REMOTE_ADDR for throttles
```
- Django never interprets `X-Forwarded-Proto` or `X-Forwarded-Host`.
- uvicorn is the only component that decides whether a forwarded header is believed, and it
  decides from the socket peer's address.
- `core/asgi.py` refuses to load in production unless `FORWARDED_ALLOW_IPS` is a bounded list of
  IPs or CIDRs.

## Investigation
- **Current state confirmed before changing anything:**
  - `core/settings.py:390-393` had `TRUST_PROXY_SSL_HEADER` (default `not DEBUG`), which set
    `SECURE_PROXY_SSL_HEADER`.
  - `USE_X_FORWARDED_HOST` could be enabled from the environment.
  - `Procfile` `web` ran `--proxy-headers` with no `--forwarded-allow-ips`.
  - `.env.example` documented `TRUST_PROXY_SSL_HEADER` and a blank `FORWARDED_ALLOW_IPS`.
- **Django 5.2.14:**
  - `django/core/handlers/asgi.py:115-116`: `ASGIRequest._get_scheme()` returns
    `self.scope.get("scheme")`.
  - `django/http/request.py:307-320`: `HttpRequest.scheme` consults `SECURE_PROXY_SSL_HEADER`
    first, then falls back to `_get_scheme()`. Setting it to `None` makes the ASGI scheme
    authoritative.
  - `django/middleware/security.py`: `SecurityMiddleware` reads `SECURE_SSL_REDIRECT`, HSTS and
    `SECURE_REDIRECT_EXEMPT` when it is constructed, and redirects based on
    `request.is_secure()`.
  - The ASGI stack is compatible with the new design.
- **uvicorn 0.46.0:**
  - `config.py:341-342`: `forwarded_allow_ips` falls back to `$FORWARDED_ALLOW_IPS`, then to
    `127.0.0.1`.
  - `config.py:484-485`: with `proxy_headers` on, the loaded app is wrapped in
    `ProxyHeadersMiddleware`.
  - `middleware/proxy_headers.py`: only a trusted `client` gets `scope["scheme"]` and
    `scope["client"]` rewritten. `_TrustedHosts` accepts IPs and CIDR networks; only the exact
    value `*` trusts everyone. Malformed entries silently become non-matching literals, which is
    why `core/asgi.py` validates them.
- **Composition:** `core/asgi.py` routes HTTP through
  `ProtocolTypeRouter({'http': ASGIStaticFilesHandler(django_asgi_app)})`.
  - `docker-compose.yml` runs uvicorn with `DEBUG=True` and no proxy.
  - `Dockerfile` `CMD` is local-only.
  - Neither needed a change.
- **Other consumers of the scheme or client address:**
  - Only `notifications/serializers.py:41` (`build_absolute_uri`).
  - New in the working tree, from separate uncommitted H3 work: `core/settings.py:264-266`
    `'NUM_PROXIES': 0` ("uvicorn resolves REMOTE_ADDR from the explicitly trusted proxy set"), and
    anonymous `login`, `register` and `social_login` throttle scopes (`users/views.py`). Those
    buckets are keyed on `REMOTE_ADDR`, so they are correct only if `FORWARDED_ALLOW_IPS` covers
    Railway's edge (see *Compatibility*).
- **Go moderation worker** (`services/go-moderation/main.go:47-50`): calls
  `/api/internal/moderation/*` over Railway's private network on plain HTTP. It is not a trusted
  proxy, so its requests keep scheme `http`. `SECURE_REDIRECT_EXEMPT = [r'^api/internal/']` keeps
  them from being redirected.
- `core.asgi` is also imported by `users/test_end_to_end.py`, which is why the startup guard reads
  `DEBUG` from the environment. Django's test runner forces `settings.DEBUG = False` before it
  imports test modules.

**`Procfile`** (`web`):
```

```
Proxy-header processing stays on, and the trusted set comes explicitly from the deployment
environment. No CIDR is hardcoded and `*` is not used.

**`core/asgi.py`**: new `require_trusted_proxies(debug, value)`, called right after

  `<verified Railway trusted proxy CIDR>`;
- any `/0` range (`0.0.0.0/0`, `::/0`).

**`.env.example`**: replaced the `TRUST_PROXY_SSL_HEADER` and blank `FORWARDED_ALLOW_IPS` lines with:

It is documented as a uvicorn deployment value: verified with Railway, never `*`, `0.0.0.0/0` or
`::/0`, required when `DEBUG=False`, not needed locally.

**`core/test_security.py`**: see *Tests*.

## Why this fixes it
- **Raw forwarded headers.** A peer outside `FORWARDED_ALLOW_IPS` can no longer make Django treat
  a request as HTTPS or change its host. uvicorn ignores its forwarded headers, and Django ignores
  forwarded headers entirely.
- **HTTPS behind Railway.** The edge's `X-Forwarded-Proto: https` is applied by uvicorn only when
  the edge's peer address is in the configured range, so HTTPS detection is peer-authenticated.
- **Configuration mistakes.** A missing, catch-all or malformed `FORWARDED_ALLOW_IPS` stops the web
  process at startup with a named error. The alternatives would be a silent redirect loop, or
  trusting everyone again.
- **Earlier hardening still holds:** host validation, secure/HttpOnly/SameSite cookies, the HTTPS
  redirect and HSTS, the internal-route redirect exemption, and the C1 CORS/CSRF settings.

## Compatibility / deployment notes

### Required Railway environment variables (web service)

| Variable | Value | Notes |
|---|---|---|
| `FORWARDED_ALLOW_IPS` | `<verified Railway trusted proxy CIDR>` | **New and required.** The address range Railway's edge proxy connects from. It must come from Railway (documentation or support) and be confirmed stable. Never `*`, `0.0.0.0/0` or `::/0`. Without a valid value, the web process exits at startup with `ImproperlyConfigured: FORWARDED_ALLOW_IPS …`. |
| `ALLOWED_HOSTS` | public host(s), plus the private hostname the Go worker uses | Required since C1/M11 |
| `DEBUG` | `False` | |
| `CSRF_TRUSTED_ORIGINS` | empty, or exact origins | Wildcards refuse startup (C1) |
| `CORS_ALLOWED_ORIGINS` | exact web-frontend origin, if still used | C1 |
| `SECURE_HSTS_SECONDS` | optional; default `3600` | Raise only after verification |

`TRUST_PROXY_SSL_HEADER` and `USE_X_FORWARDED_HOST` are no longer read. If either was added to
Railway, it has no effect and can be deleted.

### What a wrong or missing value does
- **Missing, malformed or catch-all:** the web process refuses to start (release and worker are
  unaffected).
- **Valid but not covering Railway's edge:** every public HTTPS request is seen as HTTP and
  redirected to itself, an HTTPS redirect loop. HSTS is not sent. Admin CSRF same-origin checks
  fail, and the anonymous login/register/social throttles (H3 work) see the proxy's address for
  every client, so all clients share one bucket.
  - **Recovery:** correct `FORWARDED_ALLOW_IPS`. As a short-term emergency only,
    `SECURE_SSL_REDIRECT=False` stops the loop but leaves the scheme wrong.
- **Wider than Railway's edge:** any peer inside the extra range, such as other services on a
  shared private network, can assert HTTPS and a client address.

### Finding the range (do not guess)
- **Preferred:** confirm with Railway documentation or support which addresses their edge proxy
  uses to connect to services, and whether that range is stable.
- **Empirical check, outside production:**
  1. In a non-production Railway environment, set `FORWARDED_ALLOW_IPS` to a documentation address
     that trusts nobody (e.g. `192.0.2.1`; it passes the guard) and `SECURE_SSL_REDIRECT=False`.
  2. Send several requests over time.
  3. Read the peer address in uvicorn's access log lines
     (`INFO: <peer>:<port> - "GET /api/users/terms/ HTTP/1.1" 200`).

  Observed addresses are evidence, not proof of the full or stable range; confirm with Railway
  before trusting a CIDR.

### Local development
Unchanged. `DEBUG=True` skips the guard. `docker-compose.yml` and `runserver` need no
`FORWARDED_ALLOW_IPS`.

## Remaining risk
- **`FORWARDED_ALLOW_IPS` is unverified.** The correct Railway range has not been supplied, so the
  deployed behaviour is unproven. This is why the status is NEEDS EXTERNAL ACTION.
- **Trust is only as narrow as the configured range.** If Railway's edge connects from a range
  shared with other tenants' traffic or with the project's private network, peers in that range
  can assert HTTPS and a client address. That can only be settled with Railway.
- **Header overwrite is unconfirmed.** Whether Railway overwrites or appends a client-supplied
  `X-Forwarded-Proto` is unknown until post-deploy step 5. uvicorn accepts only the exact values
  `http`, `https`, `ws` or `wss`, so an appended list is not treated as HTTPS.
- **HSTS rollout warnings.** W005 and W021 remain until the rollout completes.
