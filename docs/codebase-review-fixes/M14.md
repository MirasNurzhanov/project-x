# M14 — Club WebSocket write path skips validation performed by REST

## Status
FIXED

Club messages sent over the socket and over REST now validate through one serializer. The history
cursor `?before=` is parsed and bounded. Malformed input gets a validation error and never a stored
row or a 500. Backend tests pass and fail against the old code. No deployment was performed.

## Severity
Medium

## Original problem
Review, page 29:
- `message_type` from the socket went straight into `ClubMessage.objects.create()`, which does not
  enforce `choices`. Any string was stored, and anything over 20 characters raised `DataError`.
  The REST view validated the same field.
- A client could make an ordinary message render as a meetup proposal card.
- `?before=` on the club message list was passed unparsed to `id__lt`, so a non-numeric value was a
  500.
- Club message content had no length bound.

## Root cause
The socket write path in `clubs/consumers.py` was written separately from `ClubMessageListView.post`
and did not inherit its checks. Neither path had a shared input definition.
- The socket read `data.get('content', '').strip()` and `data.get('message_type', 'text')`, so a
  non-object JSON frame or non-string content raised `AttributeError` inside the consumer.
- REST read `request.data.get('content', '').strip()` (the same crash for non-strings) and quietly
  replaced an unknown `message_type` with `text`.
- `ClubMessage.content` is an unbounded `TextField`.
- The list view used `qs.filter(id__lt=request.query_params.get('before'))` with no parsing.

## Investigation
- **`clubs/consumers.py` `ClubChatConsumer.receive`** (already modified by separate uncommitted H1
  work; that work was preserved):
  - JSON errors were handled.
  - `data` was assumed to be an object.
  - `content` was not type-checked or bounded.
  - `message_type` was unchecked.
- **`clubs/views.py` `ClubMessageListView`:**
  - `get`: `before_id` unparsed.
  - `post`: `.strip()` on the raw value, `message_type` coerced to `text` when unknown, no length
    limit.
- **`clubs/views.py` `ClubEventListCreateView.post`:** the only legitimate writer of
  `MEETUP_PROPOSAL` messages, always with an attached `event`. Clients never need to set
  `message_type`.
- **`clubs/models.py` `ClubMessage`:** `message_type` `CharField(max_length=20, choices=…)`,
  `content` `TextField`.
- **Mobile (`aura-mobile/app/clubs/[id]/chat.tsx`):**
  - The chat input has `maxLength={2000}`.
  - The socket sends `JSON.stringify({ content: trimmed })`.
  - REST sends `{ content }` or a multipart image.
  - History pages with `?before=${oldestId}`.
  - No client sends `message_type`.
- **No existing club test** exercised `message_type`, content length or the cursor
  (`clubs/tests.py` only posts `{'content': 'hi'}`).

## Changes made
- **`clubs/serializers.py`:**
  - `MESSAGE_MAX_CHARS = 2000`, matching the app's input limit.
  - `MESSAGE_ID_MAX = 2**63 - 1`, the largest `BigAutoField` id, so a cursor cannot overflow the
    database parameter.
  - `ClubMessageInputSerializer`, the one input definition for both write paths:
    - `content`: `CharField(max_length=2000, allow_blank=True, default='')`. It rejects
      non-strings (lists, objects, booleans) and trims whitespace.
    - `message_type`: `ChoiceField(choices=[text], default=text)`, with a fixed
      `Unsupported message_type.` message that never echoes the input.
  - `ClubMessageCursorSerializer`: `before = IntegerField(min_value=1, max_value=MESSAGE_ID_MAX, required=False)`.
  - `first_error(errors)`: the first human-readable message from a DRF errors structure, used by
    both paths.
- **`clubs/views.py`:**
  - `ClubMessageListView.post` validates `request.data` with `ClubMessageInputSerializer`. It
    returns 400 `{'detail': <first error>, <field>: [...]}` before screening or any write. The
    existing "content or image is required" rule is kept.
  - `ClubMessageListView.get` parses `?before=` with `ClubMessageCursorSerializer` after the
    existing access checks. Invalid values get 400; an empty `?before=` is treated as absent.
  - Helper `_invalid(serializer)` builds that 400.
- **`clubs/consumers.py` `receive`:**
  - Validates each parsed frame with the same `ClubMessageInputSerializer`, and sends
    `{'type': 'error', 'detail': first_error(...)}` on failure. The socket stays open, nothing is
    stored, nothing is broadcast.
  - The existing "content is required" check, membership re-check, moderation screening and the H1
    suspension check are unchanged.

`message_type` validation now rejects rather than silently coercing, which only affects clients
that send the field. The app does not.

## Why this fixes it
- **One definition.** Both write paths validate through the same serializer, so neither can drift
  weaker again.
- **`message_type`.** A client can only produce `text`. `meetup_proposal` stays reserved for the
  event endpoint, which creates it with its event, and oversized values can no longer reach the
  database (`DataError`).
- **Content.** Bounded at 2000 characters on both paths, and type-checked, so non-string input is a
  validation error rather than an `AttributeError`.
- **Malformed frames.** Non-object JSON (lists, strings, numbers) fails serializer validation
  ("Invalid data. Expected a dictionary…"), so the consumer answers with an error frame instead of
  crashing.
- **Cursor.** `?before=` is an integer in `[1, 2**63-1]` or a 400. It can no longer raise
  `ValueError` (500), or overflow PostgreSQL's bigint parameter.

## Compatibility / deployment notes
- **No migration.** Existing messages longer than 2000 characters are unaffected; the limit
  applies to new writes.
- **Current app builds** send only `content`, capped at 2000 characters by the input, and numeric
  cursors, so they are unaffected.
- **REST validation errors** now carry field errors next to `detail`. The app reads `detail`.
- **Clients sending an unknown `message_type`** used to get it silently coerced to `text` over REST
  and stored as-is over the socket. Both paths now reject it.

## Remaining risk
- **DM socket.** The review also noted the direct-message socket (`friends/consumers.py`) has no
  length bound. That path is outside this batch's club scope and is unchanged.
- **`image_url`.** REST still takes it unvalidated (`(request.data.get('image_url') or '').strip()`),
  covered by a separate finding (M2). A non-string `image_url` could still raise there. It was
  left alone to keep this change narrow.
- **Length limit.** 2000 characters is a product limit taken from the app's input. Raising it
  means changing `MESSAGE_MAX_CHARS` and the app together.
