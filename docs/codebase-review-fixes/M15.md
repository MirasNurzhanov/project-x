# M15 — Account deletion had no reauthentication and immediately cascaded

Status: implemented and tested; deployment must apply the migration and schedule
the finalizer. No deployment or production deletion was performed.

## Authentication and request

`GET /api/users/delete/` gives the authenticated owner their available password
and linked-provider methods and the 30-day grace period. `DELETE` requires the
current password or a Google/Apple identity token verified by the existing
signature, issuer, audience and expiry checks. Social proof must match an
already linked `(provider, sub)` and have an `iat` no more than five minutes
old. Email matching, automatic identity linking, and an app JWT alone cannot
authorize deletion. Provider issuance time is checked; this does not claim
that every provider forces password entry instead of its native account sheet.
The endpoint is limited to five requests per minute per authenticated user.

The phone requests a fresh provider identity without replacing its Approx
session (Google clears its cached sign-in first). Password users enter their
current password in a secure text field. Both paths require explicit destructive
confirmation. The client signs out only after a `202 pending_deletion` response;
errors and provider cancellation remain visible and retryable. A lost response
cannot prove whether the server accepted a request, so the UI says “not confirmed”.
Old clients without proof are rejected and require the app update.

## Grace period and finalization

`users.0037` adds nullable lifecycle timestamps and a nullable unique
`retired_account_id`. It changes no existing account data and deletes no rows.

An accepted request atomically sets `is_active=False`, records its deadline,
turns off map sharing, clears device and legacy push tokens, and blacklists
outstanding refresh tokens. Access authentication, password/social login,
refresh and socket checks reject deletion state. Existing sockets stop on
their next inbound or outbound event. Profiles, discovery and published-content
visibility exclude pending/retired accounts. Already dispatched push messages
cannot be recalled. The original rows and evidence remain during the grace period.

The finalizer locks and rechecks a due account, transfers shared history and
evidence to a new inactive, credential-free “Deleted account” identity, then
hard-deletes the original account. This retains:

- Both participants' message records, with the deleting participant's copy hidden.
- Club messages, club/event ownership references, stories, Swifts and comments.
- ContentReport and SwiftReport rows, original snapshots and media references.
- ModerationAction subjects/reviewers, and existing block relationships.

The placeholder carries only a synthetic username/email and the original numeric
account ID for resolving old conversation URLs. Passwords, social identities,
devices, profile fields and location are not copied. It cannot authenticate or
appear in discovery. Transferring retained content avoids cascading away reports
or other people's history through the original account's foreign keys.
Transaction failure rolls back both transfers and deletion; concurrent finalizers
produce one placeholder. No blanket media-storage deletion or historical evidence
purge is performed. Storage cleanup and evidence retention periods require a
separate policy; retained content may itself contain personal information.

## Deployment operation

1. Apply migrations through the deployment migration step.
2. Deploy the API and mobile update together.
3. Configure a scheduled backend job, for example hourly:
   `python manage.py purge_deleted_accounts --execute --limit 100`.
4. Without `--execute`, the command is a read-only dry run. The limit is bounded
   to 1–1000; larger backlogs need repeated batches. It uses the deployment's
   normal database settings. Never run it against an unintended environment.

There is no public self-service cancellation endpoint in this batch. Grace-period
recovery requires a separately verified support operation; simply setting
`is_active=True` cannot restore an account with pending-deletion state. The
finalizer must be scheduled externally; a web request never performs final deletion.
