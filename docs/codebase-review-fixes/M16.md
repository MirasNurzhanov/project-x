# M16 — Bounded DM history and explicit read acknowledgements

Status: FIXED. Verified 2026-09-14. No deployment.

## Problem and API contract

GET previously loaded the whole DM conversation and marked its messages read as a side effect.
`MessagesView.get` now returns a bounded page without changing read state.

GET `/api/friends/messages/<user_id>/?before=<id>&limit=<count>`:

- Omit `before` for the latest page. Supply the returned `next_before` for the next older page.
  The boundary is exclusive: only message IDs less than `before` are eligible.
- `before` must be an integer from 1 through `2^63 - 1`. Invalid, negative, zero, overflowing
  or fractional cursors return 400. `limit` defaults to 50 and must be between 1 and 100.
- Response: `{results: [...], next_before: <id or null>, has_more: <boolean>}`.
  Results within a page are in ascending ID order. Selection uses descending IDs and one extra
  row to detect another page. Equal timestamps and newly inserted messages cannot shift the
  older-page boundary.
- Existing connection, block and per-side deletion gates remain applied. Serialization loads
  related senders with the page. Fetching history performs no read-status UPDATE.

POST `/api/friends/messages/<user_id>/read/` with `{through_id: <id>}` is the explicit read action.
The required integer uses the same bounds. It must identify a visible inbound message in that
conversation; foreign-thread, outgoing, hidden and missing anchors return 404. Connected-user
authorization and block gates still apply. The endpoint marks only visible incoming unread
messages up to that ID, returning `{read_through: <id>, updated: <count>}`. Repeating an
acknowledgement is safe. Newer messages remain unread.

## Client behavior

`hooks/useDirectMessages.ts` consumes the page envelope for initial fetches, reconnect catch-up
and “Load older messages”. A pending older-page request cannot start a duplicate fetch. Pages
merge by message identity, retain pending bubbles and discard responses for an old route.
Errors remain visible with a retry action. Adding older messages does not change the screen's
last-message scroll trigger; the list preserves visible content position.

The DM FlatList supplies viewability events to the hook. Only visible inbound messages on the
focused foreground screen trigger an acknowledgement, using the highest visible inbound ID.
GET, background delivery and socket receipt alone never acknowledge reads. Foreground/focus
and reconnect can retry a previously unsuccessful read acknowledgement. Messages arriving after
the visible boundary are not included.

This deliberately changes the DM history response from an array to a page envelope. All mobile
DM history callers were updated; the separate unread-breakdown route is unchanged. Backend and
mobile must be released together with the M4 message-ID migration. Older installed clients that
expect an array need an update; this batch does not introduce API version negotiation. The read
endpoint itself requires no new database field.

## Regression evidence

`friends/test_chat_reliability.py` covers a 65-message history with identical timestamps, a
concurrent new arrival between pages, validation bounds, no read writes during GET, idempotent
read acknowledgements, preservation of newer unread messages, hidden/deleted rows and
relationship/foreign-thread gates. Frontend regressions cover page loading, multi-page catch-up,
an initially empty conversation, visible-only reads, background/blur suppression and stale
responses. The actual DM screen is checked for its pagination and viewability wiring.
