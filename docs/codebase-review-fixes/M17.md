# M17 — Important storage dependencies are unpinned

## Status
FIXED

**Pinning and the lock file**
- Every direct backend dependency, including `boto3` and `django-storages`, is pinned exactly in the
  new `requirements.in`.
- `requirements.txt` is now generated from it with uv and locks all 68 packages, transitive ones
  included.
- `gunicorn` was confirmed unused and removed.
- `daphne` stays, because `runserver` depends on it.

**CI**
- CI now fails if `requirements.txt` drifts from `requirements.in`.
- CI runs `pip-audit` in its own job.
- Neither step has run on GitHub yet.

**The audit, run locally**
- The first run reported 49 unique advisories across 13 locked packages.
- With your approval, those packages were upgraded to the smallest versions that fix them.
- The audit is now clean against both PyPI and OSV.
- The full backend suite passes on the upgraded environment.

No deployment was performed.

## Severity
Medium

## Original problem
Review, page 31 (`requirements.txt:7-8`):
- `boto3` and `django-storages[s3]` had no versions in an otherwise pinned manifest, and they are the
  pair all media storage depends on.
- Two deploys of the same commit could install different code. A django-storages change could break
  every upload and media URL with no matching commit.
- There was no lock file or compile setup, so transitive dependencies were unpinned throughout.
- `gunicorn==26.0.0` was pinned but never used, and `daphne` was in `INSTALLED_APPS` while uvicorn
  serves ASGI.
- The reviewer ran no vulnerability scan and invented no CVEs.

**Suggested fix:**
1. Pin both to the resolved versions.
2. Generate `requirements.txt` from a `requirements.in`.
3. Add `pip-audit` to CI.
4. Drop gunicorn.

## Root cause
- `requirements.txt` was hand-maintained. It mixed direct dependencies with some transitive ones.
- The two storage packages were added without versions.
- The rest of `boto3`'s tree (`botocore`, `s3transfer`, `jmespath`, `python-dateutil`) was never
  listed, and neither were several other transitive packages: `anyio`, `hiredis`, `httptools`,
  `psycopg-binary`, `psycopg-pool`, `uvloop`, `watchfiles`, `websockets` and more. All of them
  floated.
- Nothing generated the file or checked it.

## Investigation
- **Storage use.** `core/settings.py:445-450` uses `storages.backends.s3boto3.S3Boto3Storage` against
  the R2 endpoint. Every upload and media URL goes through it.
- **Versions under test.** The project virtualenv (Python 3.13) had `boto3==1.43.79`,
  `botocore==1.43.79`, `s3transfer==0.19.2` and `django-storages==1.14.6`.
- **Direct vs transitive**, from `scratchpad/m17_dependency_map.py`. The script parses every import in
  project code, maps it to installed distributions, and builds a reverse-dependency map from package
  metadata. No network was used.
  - **Imported directly:** Django, asgiref, DRF, simplejwt, PyJWT, requests, channels, dj-database-url,
    python-decouple, orjson and Pillow.
  - **Used through configuration strings:** channels_redis, django-cors-headers, psycopg, redis,
    django-storages/boto3, daphne and uvicorn.
  - **`cryptography`** appears only in test imports, but it is a runtime dependency. PyJWT needs it
    for RS256 verification of Google and Apple identity tokens (`users/socialauth.py:168-171`) and for
    ES256 signing of the Apple Music developer token (`users/applemusic.py:120-124`).
  - **`requests-oauthlib`** is imported nowhere and required by no other package. It was kept, with a
    comment, rather than removed without review.
  - Everything else in the old file is required by another package, so it is locked as transitive.
  - No third-party module imported by project code was missing from the manifest.
- **gunicorn is unused.** Nothing runs it and nothing imports it:
  - The Procfile, the Dockerfile `CMD` and `docker-compose.yml` all run uvicorn.
  - CI never starts a server.
  - `services/go-push/k8s/deployment.yaml` only mentions "gunicorn/uvicorn worker" in a comment.
  - The remaining mentions are comments about worker processes in `notifications/push_dispatcher.py`,
    `regions/upstream.py`, `regions/nominatim.py` and `regions/test_throttle.py`.
  - No package lists it as a dependency.
- **Daphne's purpose.**
  - It is the first entry in `INSTALLED_APPS` (`core/settings.py:30`), where it replaces `runserver`
    with Daphne's ASGI server, so websockets work locally.
  - `README.md` documents it as the one-line rollback server.
  - It is not the production server, so it stays.
- **Tools.** uv 0.12.5 was available. pip-tools and pip-audit were not installed.
  - An offline compile failed ("asgiref was not found in the cache"), so the lock needed PyPI.
  - You approved network access for uv and pip-audit, and later approved upgrading the flagged
    packages.
- **Consumers of `requirements.txt`.** Railway's build, the Dockerfile and CI all run
  `pip install -r requirements.txt`. A generated file with environment markers keeps that interface
  unchanged.

- **`requirements.txt` (now generated).** It is produced by

    `tzdata` on Windows only; `psycopg-binary` everywhere except PyPy; `u-msgpack-python` everywhere

- **`.github/workflows/backend-ci.yml`:**
  - **New step in the `backend` job.** It installs `uv==0.12.5`, re-runs the compile command in place
    (uv keeps the pins it finds), then runs `git diff --exit-code -- requirements.txt`.
  - **New `dependency-audit` job.** It installs `pip-audit==2.10.1` and runs
    `pip-audit --no-deps --disable-pip --progress-spinner off -r requirements.txt` against the PyPI
    advisory database. It is a separate job, so a new advisory shows as its own failure.
- **`README.md`:** a "Dependencies" section explains how to edit `requirements.in`, regenerate the
  lock, move one package with `--upgrade-package`, and run the audit locally.
- **Local only, not a repository change.** The project `.venv` was brought to the upgraded lock. See
  *Verification* for a problem during that install and how it was repaired.

## Why this fixes it
- **Same commit, same versions:** every package that any deploy installs now has an exact version
  recorded in the repository.
- **Storage pinned:** the storage pair is pinned exactly, with its whole botocore tree.
- **Reproducible changes:** one documented command regenerates the lock.
- **Drift caught:** CI fails if `requirements.txt` stops matching `requirements.in`.
- **Advisories caught:** the audit job fails when a pinned version gains a known advisory.

## Tests added or changed
- **No new unit tests.** The change is to manifests and CI.
- **Regression guards:** the two CI steps above.
- **Behaviour after the upgrades:** checked by the full existing backend suite. It includes the RS256
  social-token tests (`users/test_socialauth.py`) that exercise PyJWT with cryptography.

## Verification
All commands were run from `backend/project-x` with uv 0.12.5 and the project `.venv` (Python 3.13,
Windows).

### Before upgrading
- **Offline compile:** `uv pip compile requirements.in --universal --python-version 3.12 --offline ...`
  → `No solution found ... asgiref was not found in the cache`.
- **First lock:** compiled in a scratch copy with the tested virtualenv's `pip freeze` as
  constraints, then regenerated in the repository without them. It has 68 pins, and every version
  matches the virtualenv.
  - `uv pip install --dry-run -r requirements.txt --python .venv\Scripts\python.exe` →
    `Would make no changes`.
  - An exact sync would only remove packages that are not in the lock:
    `cloudinary==1.45.0`, `django-cloudinary-storage==0.3.0`, `gunicorn==26.0.0`,
    `psycopg2-binary==2.9.11` and `pyflakes==3.4.0`.
- **Full suite on that environment:** `python manage.py test --settings=core.test_settings --noinput`
  → `Ran 1696 tests in 155.253s`, `OK (skipped=4)`.
- **pip-audit actually ran.** `uvx pip-audit --no-deps --disable-pip -r requirements.txt` (pip-audit
  2.10.1):
  - PyPI service → `Found 90 known vulnerabilities in 13 packages`.
  - `-s osv` → `Found 95 known vulnerabilities in 13 packages`.
  - JSON output (`-f json --desc on`, saved in `scratchpad/m17_pip_audit.json`) → 49 unique advisory
    IDs, counted per package in the table above.
  - The IDs are those the tool reported. For example: `PYSEC-2026-175` to `-179` (PyJWT),
    `PYSEC-2026-3696` to `-3699` and `-3923` (sqlparse), `PYSEC-2026-160` (Twisted),
    `PYSEC-2026-2294` (ujson), `PYSEC-2026-141` and `-142` (urllib3), and `PYSEC-2026-3552` to `-3554`
    (cryptography, with CVE aliases).
  - Their impact on this application was not assessed one by one. They were resolved by upgrading.

### Upgrade and lock
- **Compile:**
  `uv pip compile requirements.in --universal --python-version 3.12 -o requirements.txt -c upgrade-constraints.txt -P <the 13 packages>`
  → exit 0. The changed pins are exactly the table above.
- **Clean regeneration:** the command was then re-run without the constraints file. Pins stayed
  identical (68), and no scratchpad annotations were left.

### Installing into `.venv`
1. **uv failed.** `uv pip install -r requirements.txt` stopped with
   `failed to remove directory ...\daphne-4.2.1.dist-info\licenses: Access is denied (os error 5)`.
   - The virtualenv's package folders carry the read-only attribute on this OneDrive-synced desktop,
     and uv does not clear it.
   - None of the other 13 upgrades had been applied at that point, but the aborted attempt had
     already deleted Daphne's package files and most of its `dist-info`.
2. **pip upgraded the rest.** `.venv\Scripts\python.exe -m pip install -r requirements.txt` upgraded
   the other 13 packages, then stopped at Daphne with `uninstall-no-record-file`.
3. **Daphne repaired.** `pip install --ignore-installed --no-deps daphne==4.2.2`.
   - The leftover `daphne-4.2.1.dist-info` was inspected first: it held no files, only an empty
     `licenses` folder.
   - Its read-only attribute was cleared and it was removed.
   - `importlib.metadata.version('daphne')` → `4.2.2`, with 32 package files.
4. **Final state:**
   - `uv pip install --dry-run -r requirements.txt --python .venv\Scripts\python.exe` →
     `Would make no changes`.
   - `pip check` → `No broken requirements found`.

### After upgrading
- **pip-audit:** `uvx pip-audit==2.10.1 --no-deps --disable-pip --progress-spinner off -r requirements.txt`
  → `No known vulnerabilities found` (exit 0). The same with `-s osv` → `No known vulnerabilities found`
  (exit 0). pip-audit printed a warning recommending hashed requirements.
- **Full suite** (Git Bash): `python manage.py test --settings=core.test_settings --noinput` →
  `Ran 1696 tests in 74.930s`, `OK (skipped=4)`.
- **Migrations:** `python manage.py makemigrations --check --dry-run --settings=core.test_settings` →
  `No changes detected`.
- **System check:** `python manage.py check --settings=core.test_settings` →
  `System check identified no issues (0 silenced).`
- **Deploy check:** `check --deploy --fail-level WARNING --settings=core.settings`, with the
  environment values CI's deploy step uses → `System check identified no issues (0 silenced).`
- **Daphne smoke test** (`scratchpad/smoke_daphne.py`: `manage.py runserver` on localhost with
  `DEBUG=True`, killed afterwards):
  - `GET /api/regions/1/` → `401`.
  - The server log line `HTTP GET /api/regions/1/ 401 [0.02, 127.0.0.1:...]` is Daphne's access-log

  - No tracebacks.
- **Not re-run on the upgraded packages:** the uvicorn multi-worker smoke test from M20 (uvicorn and
  its HTTP and websocket libraries did not change), and the PostgreSQL/Redis CI job (no local

## Compatibility / deployment notes
- **What the next deploy installs.** Railway will install the upgraded versions. Most are patch or
  minor releases. Larger jumps are cryptography 48 → 50, Twisted 25.5 → 26.4, pyOpenSSL 26.2 → 26.4
  and sqlparse 0.5 → 0.6. Coverage:
  - The full suite passes locally, including the social-token verification tests.
  - Not exercised: real Google or Apple tokens, the Apple Music token, live R2 uploads, and
    PostgreSQL/Redis in CI.
- **Check the Railway start command before deploying.** You confirmed the web service has a custom
  start command but did not share its text; the earlier inspection recorded it running uvicorn. If it
  now invokes `gunicorn`, removing gunicorn breaks the deploy.
- **Python version.** The lock is resolved for Python 3.12 and later (CI and the Dockerfile use
  3.12). The same lock matched the local 3.13 virtualenv exactly. Railway's Python version was not
  verified.
- **Existing virtualenvs:**
  - `pip install -r requirements.txt` upgrades them but leaves stale packages behind;
    `uv pip sync requirements.txt` makes them exact.
  - On this OneDrive-synced machine, use pip to install into `.venv`, because uv cannot remove its
    read-only package folders.
- **Out of scope:** `loadtest/` and the Go services keep their own dependency files, which this batch
  did not touch.

## Remaining risk
- **CI not yet run.** The lock check and audit job have not run on GitHub. The lock check could fail
  if uv's output on Linux differs in any byte; that was not verified.
- **Future advisories.** Any advisory published after 2026-09-14 will fail the audit job by design,
  so upgrades need to follow promptly.
- **No hashes.** The lock has no `--generate-hashes`, so install integrity relies on PyPI and TLS
  alone.
- **Unused dependency kept.** `requests-oauthlib` (and `oauthlib`) remain installed though nothing
  imports them.
- **Advisories not assessed one by one.** The 49 advisories were removed by upgrading, not evaluated
  individually for exploitability in this app.
