## Severity and original problem
MEDIUM. Approx-Codebase-Review.pdf, page 32: arbitrary-anchor map reads were unthrottled, allowing rapid repeated spatial queries.

## Root cause and changes
`proximity/views.py` assigns the existing DRF `ScopedRateThrottle` scope `map_query` to all four read routes:

- POST `/api/proximity/nearby/query/`
- POST `/api/map/nearby/query/`
- GET `/api/proximity/nearby/`
- GET `/api/map/nearby/`

They share one per-user budget, so switching endpoints or anchor coordinates does not reset it. Limits apply before payload validation and map work. Invalid requests also consume capacity. Existing authentication, visibility, precision and read-only private-anchor semantics are unchanged. Location writes and unrelated endpoints were not changed.

`THROTTLE_MAP_QUERY` configures the rate in `core/settings.py`; `.env.example` records the default **1200/hour**. A composite map request every ten seconds costs 360/hour. Even two legacy reads per tick cost only 720/hour, leaving room for refreshes and fallbacks.

## Tests and verification
New `proximity/test_throttles.py` checks the shared threshold across all four routes, Retry-After, separate users' budgets and acceptance of 720 requests within the default hourly window. Both tests passed. Existing proximity, visibility and query behavior tests also passed in the related run: **637 tests, 636 passed, one unrelated PostgreSQL concurrency test skipped**.

The polling-volume test intentionally uses invalid bodies so it tests admission limits without expensive map queries. Existing proximity suites cover real valid queries and their privacy invariants. No physical-client polling or production load test was performed.

Django system checks pass; no migrations or dependencies changed. Production uses the existing shared cache. As with other DRF scoped throttles, simultaneous requests can slightly exceed the configured budget; no alternative throttle implementation was introduced.
