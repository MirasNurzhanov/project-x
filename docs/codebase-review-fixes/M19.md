# M19 — Safe, idempotent Hi requests

## Status
FIXED

The concurrent-writer regression now runs against a real PostgreSQL server and passes (details
under *PostgreSQL concurrency verification*, 2026-09-13). The verification exposed no defect, and
the M19 implementation and tests are unchanged. No deployment was performed.

The PostgreSQL major version used was **18.4**, not 16; see *PostgreSQL version* for why and what
remains open.

## Severity and original problem
MEDIUM. Approx-Codebase-Review.pdf, page 33: `SendHiView` looked up raw users, deleted a request
and then inserted another, and notified on every send. Concurrent requests could race the unique
constraint. Decline deleted the only record of the receiver's decision.

## Root cause and changes
- **Recipient lookup.** `friends/views.py` resolves recipients through
  `visibility.visible_users(request.user)` and returns the canonical `visibility.not_found()` for
  unavailable targets.
  - Blocked users (either direction), absent IDs, self and malformed IDs all get the same response,
    so nothing reveals whether a target exists.
  - A missing `receiver_id` is still an input-validation error.
  - Visible users still receive ordinary creation responses. This is not a blanket promise that
    authorised visible IDs cannot be identified.
- **Creation** uses `transaction.atomic()` and `get_or_create()` with the existing unique
  `(sender, receiver)` constraint. The database arbitrates concurrent inserts through that
  constraint, instead of a delete/insert gap. No model or migration change is needed.
- **Responses.** The first creation returns 201. Repeated sends return 200 with the same row
  identity, preserve its pending, accepted or rejected state, and create no further notification.
- **Push.** Only a newly created request schedules the push, through `transaction.on_commit`, so
  rolled-back creations do not notify.
- **Decline** moves pending to the existing REJECTED status instead of deleting the row. The
  sender cannot reset that decision through `SendHiView`. There is deliberately no automatic
  cooldown expiry.
- **Accept and decline** use conditional pending-state updates, so a stale read cannot overwrite a
  completed decision or generate duplicate acceptance pushes.
- **Throttling.** Hi and friend-request sends share the `social_request` scope, using the existing
  DRF scope infrastructure. `THROTTLE_SOCIAL_REQUEST` in `core/settings.py` and `.env.example`
  defaults to **30/hour per user**. Other friend-request business logic is unchanged.

Canonical visibility permits requesting a connection to a private profile. That existing behaviour
is preserved; no separate ghost/private-account policy was invented.

## Why concurrent first sends are safe on PostgreSQL
This is the sequence two simultaneous `POST /api/friends/hi/` requests for the same sender and
receiver follow, confirmed by the server log below:
1. **Both miss.** Each request's `get()` inside `get_or_create()` finds no committed row.
2. **Both insert.** Each runs the INSERT inside Django's `get_or_create` savepoint
   (`transaction.atomic(using=db)`, nested in the view's `transaction.atomic()`).
3. **The second waits.** Its INSERT finds the first request's not-yet-committed entry in the unique
   index `friends_hirequest_sender_id_receiver_id_76eb946c_uniq`, and waits for that transaction
   (`ShareLock on transaction …`).
4. **The first commits.** Its `transaction.on_commit` callback sends the single push; response 201.
5. **The second fails and recovers.** Its INSERT then fails with `duplicate key value violates
   unique constraint`. Django rolls back only the savepoint, so the view's transaction stays usable,
   and runs `get()` again. Under READ COMMITTED every statement takes a fresh snapshot, so this
   `get()` sees the first request's committed row and returns `created=False`. No `on_commit` is
   registered; response 200.

This relies on READ COMMITTED, the PostgreSQL and Django default. Nothing in `core/`, `friends/` or
`users/` sets `isolation_level`, `ATOMIC_REQUESTS` or `AUTOCOMMIT` (grep, 2026-09-13). Under
REPEATABLE READ or SERIALIZABLE, the re-`get()` in step 5 would not see the other row, and the
`IntegrityError` would reach the API as a 500.

## PostgreSQL version
- **Production major: not recorded in the repository.** `docker-compose.yml` uses
  `postgres:16-alpine` for local development only, and the live Railway database version was not
  inspectable from here.
- **Why 18.4.** No PostgreSQL 16.x build was available on this machine: no Docker, no WSL, no
  installed PostgreSQL, and none in the pip or MSYS2 package caches. The official
  `postgresql-16.15-1-windows-x64-binaries.zip` (332,441,502 bytes, `get.enterprisedb.com`) was
  not downloaded, because that requires the user's explicit approval. The already-present official
  18.4 build was used instead.
- **Why the version difference is unlikely to matter.** The behaviour exercised here is the same
  in PostgreSQL 16 and 18: a btree unique-index insert waits on the in-progress inserting
  transaction and then raises a unique violation, and READ COMMITTED takes a per-statement snapshot.
  This is an explanation, not a 16.x test result.
- **Still open, and not claimed as done:**

  - Confirming production's actual major version.
  - The separate, uncommitted `.github/workflows/backend-ci.yml` would run `friends.test_hi_abuse`
    against `postgres:16` through `core/ci_test_settings.py` once committed. It has not run.

## Operational boundary
- **Throttle budgets.** Deployments need the existing shared Redis cache to share budgets across
  workers. DRF counters are approximate during concurrent bursts; request-row uniqueness is
  enforced by the database regardless of throttling.
- **Isolation level.** The concurrent-send guarantee depends on READ COMMITTED (see *Why concurrent
  first sends are safe*). Changing the database isolation level requires revisiting `SendHiView`.
- **Rejected rows** persist until account deletion or an explicit future lifecycle policy.
- **Accept/decline routes** keep their original success shapes and statuses.
