# M2 — Arbitrary image URLs on message writes

Status: fixed in code; tests pass. No deployment performed.

New direct-message and club-message writes refuse the `image_url` field, including
empty/null values, URL-plus-text and URL-plus-file requests. DM idempotent replays
do not bypass this check. Both WebSocket consumers reject URL fields as well.
Club REST/socket validation shares `ClubMessageInputSerializer`.

New images must use the existing multipart `image` field. The mobile DM and club
chat screens already use that path; no incompatible client rewrite was needed.
Historical model `image_url` fields and serializer fallbacks remain unchanged,
so existing legacy images remain readable. No records/files were removed and
no schema migration is needed for this finding.

`core.test_message_media` adds six tests covering all four write paths, invalid
values, file-plus-URL rejection, idempotency, valid PNG uploads and legacy reads.
The focused message/friends/club tests passed (44 tests, one PostgreSQL-only skip
on SQLite). The combined PostgreSQL/Redis regressions passed all 80 tests.

M3 remains separate and unfinished: rejecting external URLs alone does not prove
uploaded files have safe contents, sizes, MIME types or serving permissions.
