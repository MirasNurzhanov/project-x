# M20 — Only one uvicorn worker is configured

## Status
NEEDS EXTERNAL ACTION (code complete)

The code side is done and tested:
- The Procfile starts `WEB_CONCURRENCY` uvicorn workers, default 2.
- A production start refuses more than one worker without Redis.
- A production start refuses a worker count whose connection pools exceed a declared database limit.

What the repository cannot show:
- whether production runs this start command;
- how much CPU and memory the Railway service has;
- the database's connection limit.

An earlier read-only inspection (`docs/scaling-railway.md`) recorded a Railway start-command override that bypasses the Procfile. No deployment was performed.

## Severity
Medium

## Original problem
Review, page 34 (`Procfile:2`, `core/settings.py` `DB_POOL_MAX_SIZE = 12`):
- uvicorn defaults to one worker. Every sync Django view runs in that one process's thread pool,
  under one GIL.
- The GIL is shared by CPU-bound map geometry (H5), long Swift uploads and the AI moderation threads.
- The connection pool is per process, so total database concurrency was 12.
- The settings already budget "processes × DB_POOL_MAX_SIZE", but the process count was never set.
- **Suggested fix:** `--workers 2`, sized against CPU and the PostgreSQL limit with headroom for a
  migration and a psql session. The review also notes that Channels needs Redis for cross-process
  groups.

## Root cause
The `web` command had no `--workers` and nothing set `WEB_CONCURRENCY`, so uvicorn ran one process.
Nothing tied the process count to the pool size, or to Redis being present.

## Investigation
- **uvicorn 0.46.0 worker count.** `--workers` defaults to `None`. `uvicorn/config.py:337-338` then
  reads `WEB_CONCURRENCY` if set, otherwise uses 1.
- **uvicorn restarts dead workers.** `uvicorn/supervisors/multiprocess.py:163-180`
  (`keep_subprocess_alive`) logs `Child process [pid] died` and starts a replacement. Each child
  imports the application itself. With several workers, an import-time startup guard therefore makes
  uvicorn restart children indefinitely instead of exiting. That includes M11's
  `require_trusted_proxies` and the new check below. Smoke test B confirms it.
- **State that must be shared across workers:**
  - `CHANNEL_LAYERS` (`core/settings.py`) is always `channels_redis.core.RedisChannelLayer`, with
    hosts `[REDIS_URL]` (default `redis://localhost:6379`). With a real `REDIS_URL`, group sends
    reach sockets on other workers.
  - `CACHES` uses Redis when `REDIS_URL` is set and `LocMemCache` otherwise. DRF throttles use the
    default cache, and so does `regions.nominatim`'s one-request-per-second `cache.add` gate.
    Without Redis, each worker would keep its own budget.
  - A search of non-test code for `lru_cache`, `functools.cache`, `threading.Lock()`,
    `ThreadPoolExecutor(` and module-level dict caches found no matches.
  - Swift AI moderation claims each job with a conditional database update, so duplicate workers do
    not process a job twice.
- **Migrations.** `migrate` runs once per replica before uvicorn starts, so extra workers do not
  multiply migrations. That `web` migrates on every boot at all is H7, which is not in this batch.
- **Tests.** `users/test_end_to_end.py` imports `core.asgi` inside the test process.
  `core/test_settings.py` puts `DEBUG=True` in the environment, so the startup checks are skipped
  there, as M11's already were.
- **CI.** The `check --deploy` step does not import `core.asgi`.
- **Railway (7 September inspection in `docs/scaling-railway.md`).**
  - The API start command was overridden to
    `sh -c 'python manage.py migrate && uvicorn core.asgi:application --host 0.0.0.0 --port 8000'`.
  - Services ran one replica each.
  - `WEB_CONCURRENCY`, CPU/RAM limits and the database connection limit were not established.

## Changes made
- **`Procfile` `web`:**
  ```
  python manage.py migrate && python manage.py fix_age_tiers && python -c "import core.asgi" && uvicorn core.asgi:application --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips="$FORWARDED_ALLOW_IPS" --workers "${WEB_CONCURRENCY:-2}"
  ```
  The pre-flight import runs every startup guard once in the foreground: M11's proxy check and the
  capacity check below. A bad configuration then stops the start instead of looping.
- **`core/capacity.py` (new):**
  - `DEFAULT_WEB_WORKERS = 2`.
  - `web_workers(environ)`: blank means 2. A non-integer or a value below 1 raises
    `ImproperlyConfigured`.
  - `connection_budget(workers, pool_max_size, reserve)`.
  - `require_worker_capacity(...)`:
    - Skipped when `DEBUG` is on.
    - Refuses more than one worker when `REDIS_URL` is empty.
    - When pooling is on and `DB_MAX_CONNECTIONS` is non-zero, refuses a budget above it. The message
      spells out the arithmetic.
- **`core/asgi.py`:** calls `require_worker_capacity` right after `require_trusted_proxies`. `DEBUG`
  and `REDIS_URL` are read through `decouple`, as `settings.py` reads them.
- **`core/settings.py`:** `DB_CONNECTION_RESERVE` (default 20) and `DB_MAX_CONNECTIONS` (default 0,
  meaning unchecked), with the budget explained beside the pool settings.
- **`core/test_security.py`:** the M11 test's successful `core.asgi` import now also sets
  `REDIS_URL`. With `WEB_CONCURRENCY` unset, the default of two workers requires it. The refusal
  case in that test is unchanged.
- **Documentation:**
  - `.env.example`: `WEB_CONCURRENCY`, `DB_POOL_MAX_SIZE`, `DB_CONNECTION_RESERVE` and
    `DB_MAX_CONNECTIONS`, commented with defaults.
  - `README.md`: pool table rows.
  - `docs/scaling-railway.md`: new "Web worker processes" section.

## Why this fixes it
Production now runs two uvicorn processes by default. Each has its own event loop, thread pool, GIL
and connection pool, so CPU-bound work is spread over two processes and database concurrency is
2 × 12 = 24.

The two configurations that would make multiple workers wrong cannot start with `DEBUG` off:
- no shared Redis, which would split channel groups, throttles and the cache;
- pools that exceed the declared database limit.

Connection budget per replica is `WEB_CONCURRENCY × DB_POOL_MAX_SIZE + DB_CONNECTION_RESERVE`:

| Workers | Pool max | Reserve | Connections |
|---|---|---|---|
| 2 (default) | 12 | 20 | 44 |
| 4 | 12 | 20 | 68 |

The reserve covers:
- the `worker` (moderation) process's own pool, up to `DB_POOL_MAX_SIZE`;
- the release migration;
- an admin session.

## Compatibility / deployment notes
**Required in Railway before this reaches production.** This is why the status is NEEDS EXTERNAL
ACTION.
1. **Start command.** Open the web service's start command. If the override recorded in
   `docs/scaling-railway.md` is still set, the Procfile `web` line is not used. That means none of
   M11's proxy flags, this pre-flight or `--workers` apply. Remove the override, or make it match
   the Procfile line exactly.
2. **`REDIS_URL`** must be set on the web service. With two or more workers the process refuses to
   start without it.
3. **`WEB_CONCURRENCY`:** set it explicitly for the service's vCPU allocation. Start at 2. Each
   worker loads Django separately, so check the plan's memory limit too.
4. **`DB_MAX_CONNECTIONS`:** look up the database's `max_connections` and its reserved connections,
   split the usable number between web replicas, and set it. Keep `DB_CONNECTION_RESERVE` large
   enough for the `worker` process's pool (up to `DB_POOL_MAX_SIZE`), the release migration and
   admin access.
5. **After deploying, check:**
   - The logs show `Started parent process` and one `Started server process` per worker.
   - The connection count in `pg_stat_activity` stays inside the budget under load.
   - Two clients in the same club chat, likely on different workers, both receive each other's
     messages.

**Other notes:**
- **Local development:** unchanged. `runserver` and `docker-compose.yml` run with `DEBUG=True`,
  which skips both checks. uvicorn without `--workers` still starts one process unless
  `WEB_CONCURRENCY` is set.
- **Startup time:** the pre-flight adds one application import. That took 1.9 s locally in smoke
  test C.
- **Unchanged:** the `release` and `worker` Procfile entries.
- **Commit state:** commit `8af6002`, already on `origin/main`, contains `core/capacity.py` and its
  tests but not the Procfile, `asgi` or settings changes. That tree fails `core.test_capacity`.

## Remaining risk
- **Sizing and throughput:** two workers is a starting point, not a size measured against real CPU,
  memory or traffic. Production throughput is unmeasured.
- **Budget check is off by default:** `DB_MAX_CONNECTIONS` defaults to 0, so the database budget is
  not checked until someone sets it.
- **Scope of the check:** it sees one replica only, not other replicas or other services sharing the
  database.
- **Unseen per-process state:** state the search did not find, or a future module-level cache, would
  diverge between workers without error.
- **Windows:** multi-worker uvicorn failed to listen in one child. This affects development only.
- **H7 still applies:** `web` still migrates on every boot, so concurrent replicas can still race
  migrations.
