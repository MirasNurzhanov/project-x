# M4 — Direct-message text has a visible delivery lifecycle

Status: FIXED. Verified 2026-09-14. No deployment.

## Problem and implementation

Text sent through a dead DM socket could disappear without a pending bubble or acknowledged
delivery. The previous failure path could remove an unrelated pending image. Matching messages
by their text also could not distinguish identical sends.

Mobile `hooks/useDirectMessages.ts` now creates an optimistic text bubble before starting delivery.
Every send gets a distinct UUID-shaped client ID; the temporary display ID includes that key.
Unknown sender identity leaves the draft in the input instead of submitting it anonymously.

Text sends use POST `/api/friends/messages/<user_id>/` with `content` and `client_id`, with a
15-second request timeout. This gives each message a correlated REST acknowledgement even if
the live socket is disconnected or appears open while unusable. The socket remains the live
receive transport and reconnects through the shared H8 service.

`services/chatHistory.ts` reconciles server ID or the same sender/client-ID pair across REST
acknowledgements, socket echoes and catch-up history. Identical text with distinct keys stays
distinct, regardless of acknowledgement order. A late HTTP failure after a successful echo
cannot turn a delivered message into a failed one.

Failure changes only that pending text to a visible failed bubble with its reason and a retry
action. It never removes another text or pending image. Retry retains the original client ID,
and the hook permits only one concurrent submission per ID. Pending/failed drafts live in the
mounted conversation; durable offline drafts across app termination are not introduced.

## Backend acknowledgement and idempotency

`Message.client_id` is nullable for legacy messages. The database unique constraint on
`(sender, receiver, client_id)` plus atomic `get_or_create` prevents duplicate rows on retries.
The first request returns 201; repeats return 200 with the original message, without another
push or broadcast. A changed retry body cannot overwrite the stored message. Deleted-message
retries are refused rather than resurrected.

The serializer, REST broadcast and `ChatConsumer.chat_message` echo carry `client_id`. Existing
authorization and content moderation still apply. Keyed delivery is for text only; existing
unkeyed text, uploaded images, legacy image URLs and story-reply handling retain their paths.

Deploy migration `friends/0008_message_client_id_message_unique_dm_client_message.py` before the
updated backend/client. It adds the nullable UUID field and uniqueness constraint without
rewriting old message content. The generated migration was inspected and applied successfully
when creating disposable PostgreSQL and SQLite test databases. No friends migration drift remains.

## Regression evidence

- Frontend hook tests verify pending-before-ack, submission while disconnected, reverse-order
  identical-text acknowledgements/echoes, one-message failure, pending-image preservation,
  same-key retry, one active retry per key, lost acknowledgements, and stale-route responses.
- DM screen regression verifies the failed bubble is visible and its retry action targets the
  exact message. Shared history tests prove text is never used as a reconciliation key.
- `friends/test_chat_reliability.py` verifies repeated/distinct/legacy sends, moderation/visibility
  compatibility, deletion behavior and database uniqueness. A real Channels communicator verifies
  the REST acknowledgement and socket echo share the client ID.
- Its PostgreSQL concurrent test launches two API requests on independent database connections:
  **one 201, one 200, the same message ID, one row, one notification**, with no API integrity error.

All 25 new frontend regressions passed; the full mobile suite passed **888 tests in 64 suites**.
The related backend run passed **339 of 341**, with only the two PostgreSQL-only concurrency
tests skipped on SQLite. The PostgreSQL/Redis chat regression run passed **all 17 tests**, including
the new concurrent-message and actual-echo tests. Typecheck, lint and system checks passed as
detailed with reproducible commands in [H8](H8.md). Test logs accompany the workspace reports.
