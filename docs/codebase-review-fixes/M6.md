# M6 — Secure credentials and single-use WebSocket tickets

Status: implemented and locally tested across backend/mobile. Native-device and
Railway rollout verification remain required. No deployment or EAS build was run.

## Mobile credentials

Expo SDK 54 `expo-secure-store ~15.0.8` now holds access/refresh tokens as one
JSON session entry, plus the pending logout-revocation credential in a separate
secure entry. Login, social login, request authentication, refresh, Swift upload,
startup, logout and revocation retry use this store. No new credentials are
written to AsyncStorage; it remains appropriate for non-secret preferences.

Migration is serialized with reads/writes. An existing secure session wins as a
pair, never mixed with legacy tokens. Legacy values are copied and read back
before plaintext removal; failed copying preserves the only copy for retry.
Failed cleanup is retried rather than silently declared complete. Native errors
are replaced with credential-free messages. Malformed secure data fails closed.

Logout attempts all cleanup steps even when one storage system fails. A durable,
non-secret signed-out marker prevents a failed keychain deletion from restoring
the session. Startup retries deletion. Late refresh responses use a serialized
compare-and-replace against the original refresh token and cannot overwrite a
different account or revive logout. Requests recheck session state after awaiting
credential storage. If both storage systems are unavailable, the app closes the
in-memory session and warns that device cleanup needs attention; durable cleanup
cannot be guaranteed until the OS permits writes again.

The keychain accessibility is `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, without
biometric prompts, to support the existing background-location task after first
unlock. There is no plaintext/web fallback. iOS keychain entries can survive
uninstallation; uninstall is not a substitute for logout. Native behavior follows
the [SDK 54 SecureStore documentation](https://docs.expo.dev/versions/v54.0.0/sdk/securestore/).

## Socket protocol

Authenticated `POST /api/socket-ticket/` accepts `{ "path": "/ws/notifications/" }`
(or an existing `/ws/chat/<id>/` / `/ws/clubs/<id>/` route) and returns
`{ "ticket": "<opaque 256-bit random value>", "expires_in": 30 }` with `no-store`.
Issuance is throttled at 120/minute per user.

Every mobile connection/reconnection obtains a fresh ticket using the normal
authenticated HTTPS client. Only `?ticket=...` appears in the socket URL; JWT
query authentication has been removed, not left as a fallback.

Production requires the existing Django Redis cache (`REDIS_URL`). Issuance
stores a path-bound credential under a hashed cache key for 30 seconds. Redemption
uses one Redis Lua GET-and-DELETE operation on the primary connection. This is
atomic across HTTP/ASGI workers and has no separate replay-marker crash/eviction
window. The implementation uses the pinned Django 5.2 Redis backend's key and
serializer helpers; revalidate that adapter if upgrading Django. LocMem is only
allowed with DEBUG enabled. Cache/throttle failures return a generic 503 or reject
the handshake; there is no fail-open authentication path.

Redemption reloads account standing: inactive, suspended, deletion-pending and
retired accounts are refused. Existing consumers still enforce connection/club
membership and recheck standing on incoming/outgoing events. A ticket is not an
authorization grant for the target conversation. Expiry, replay, wrong paths,
duplicate parameters, malformed queries and legacy JWTs are rejected.

Axios failures returned to callers no longer retain credential-bearing config,
request objects or native error text. Known credential fields/values are redacted
from error payloads. Temporary Google diagnostics and push-token logging were
removed. Uvicorn access/error handlers redact socket ticket/JWT query values and
bearer credentials. External Railway/CDN/proxy logging is outside this repository
and must also redact query credentials; short-lived tickets remain secrets.

## Rollout / remaining verification

1. Verify shared `REDIS_URL`, Redis Lua permission, clock synchronization, and
   query redaction at Railway's external proxy/log collectors.
2. Build a new SDK 54 native binary with the SecureStore config plugin through EAS.
   This is a native dependency change, not an OTA-only JavaScript release.
3. Coordinate server and mobile release. Old clients' JWT socket handshakes will
   be rejected; do not promise backward-compatible live chat. Their existing REST
   routes are retained. New clients need the ticket endpoint before socket use.
4. On iOS and Android test upgrade with legacy credentials, relaunch, background
   reporting after unlock, login/refresh, offline logout/revocation, account switch,
   suspended/deleted sockets, and chat reconnect. No device run was performed here.
5. Do not roll credentials back into AsyncStorage. Older binaries cannot read the
   secure session; a downgrade may require sign-in and still cannot use JWT sockets.

The existing pending offline-revocation queue holds one refresh credential, not
an unbounded queue; offline server revocation remains best-effort until expiry.
This change does not claim to solve every revocation-retention policy question.
