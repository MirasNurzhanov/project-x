# M8 — Bounded, recoverable moderation work

Status: implemented; production worker provisioning and load verification remain.

Web uploads persist their moderation job and no longer create daemon threads.
The existing `moderate_swifts --loop` service consumes the database-backed queue
sequentially. One Python worker runs one job at a time; scale only with an explicit
worker and database/provider budget. The default pass limit is 50, the poll
interval is 20 seconds; CLI values are bounded to 1..1000 and 1..3600 respectively.
`SWIFT_AI_MODERATION_SYNC` must remain false on web services.

Execution recycles old database connections before work and closes worker-owned
connections in a finally block. Empty sweeps also return their connection before
idling. Explicit synchronous callers' enclosing transactions are not closed.
Queued jobs survive process restarts, retries retain exponential backoff, and
claims now reject retries that are not due. Both Python sweeps and Go lease
requests recheck staleness at UPDATE time, so an old selection cannot reset a
newly claimed live job. Conditional database claims arbitrate competing workers.

This is recoverable, at-least-once processing, not a claim of exactly-once
inference after lease expiry. Keep the worker job budget below the stale timeout;
verify restart recovery and provider latency under production load. An enabled
moderation feature without a running worker leaves new videos safely pending.
Changing environment variables requires restarting the affected process.

Tests cover a 1,000-enqueue burst creating no threads or inline inference,
connection cleanup after success/failure, invalid limits, stale selection races,
backoff, existing retry/exhaustion behavior and real PostgreSQL concurrent claims
with one winner. Both Go service suites pass `go test -race ./...` with Go 1.23.12.
See [OPERATIONS_VALIDATION.md](OPERATIONS_VALIDATION.md).
